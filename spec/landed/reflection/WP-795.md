# WP-795 — type_of of a variable completed by a later declaration

The rule is spec/reflection-queries.md §1 (`type_of`) and §2.

- **Cause.** A variable reflection designates the entity's first
  declaration (`Sema::reflectee_of_decl`, one reflection per entity), and
  `Sema::type_of_reflectee` (`crates/kiln_sema/src/meta/query/mod.rs`)
  read that declaration's type. Each redeclaration of a variable carries
  its own type, and a later one can complete an array of unknown bound
  ([basic.types.general]/6, [dcl.array]/8; `Sema::redecl_var_type`), so
  for `struct S { static const char k[]; };` with
  `inline const char S::k[] = "SAFE";` kiln answered
  `type_of(^^S::k) == ^^const char[]` where GCC 16.1 answers
  `const char[5]` and `decltype(S::k)` is `const char[5]`. `size_of`
  (`Sema::layout_type`, `crates/kiln_sema/src/meta/member.rs`) failed on
  the same incomplete type. Found in downstream code, which reads
  the member through `members_of` and prints the type.
- **Fix.** `Sema::reflected_var_type`: a `Var` or
  `VarTemplateSpecialization` reflection has the type of the entity's
  latest declaration so far (`Ast::latest`); `type_of` and `size_of` use
  it. Because a later declaration can still complete it, a `type_of`
  answer that is an array of unknown bound marks the evaluation impure
  through the new `Oven::mark_impure` (`crates/kiln_oven/src/lib.rs`), so
  the consteval-call memo never replays it after the definition; any
  other answer stays memoizable (`type_of` remains `Stable`).
- **Tests.** `tests/conformance/meta.reflection.queries/`
  `type-of-completed-array.cpp` (`^^` and `members_of` reflections,
  `size_of`, `display_string_of`, the point before the definition, the
  namespace-scope `extern` analogue) and
  `type-of-completed-array-memo.cpp` (the same consteval call before and
  after the definition), both with the GCC 16.1 oracle;
  `tests/conformance/dcl.array/completed-by-redeclaration.cpp`
  (`decltype`, `sizeof`, member access, `&`, a bound kept by a later
  boundless declaration; kiln, clang 19 and clang 22).
- **Deviations.** None. A static data member of a class template
  specialization follows clang: its out-of-class definition is
  instantiated by `sizeof`, not by `decltype`, and `type_of` sees
  whichever declarations exist at the point of evaluation.
