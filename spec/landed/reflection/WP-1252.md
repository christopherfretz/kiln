# WP-1252 — reflect_constant of a function reflection's value instantiates nothing

The rule is spec/reflection.md §3 "Reflecting a function reflection's
value". No code changed. kiln already behaves as the standard requires.
The work package records the decision and pins it with a test.

- **Report.** The reference workload (reference-workload finding K8
  residual, against kiln 1.0.0) collects the member function reflections of
  `Panel<2>` from `members_of(^^Panel<2>, access_context::unchecked())`,
  where `template <int N> struct Panel { constexpr int operator[](int)
  const { static_assert(N == 1, "..."); ... } };`, into a
  `std::vector<std::meta::info>`, then passes them to
  `reflect_constant(v[0])`, `reflect_constant_array(v)` or
  `define_static_array(v)`. GCC 16.1 instantiates the body (the
  static_assert fires, "required from here" at the `reflect_constant`
  call, "in 'constexpr' expansion of 'walk()'"). kiln does not.
  `extract<int (Panel<2>::*)(int) const>(m)` instantiates in both
  (WP-1244), and `members_of` with `type_of` in neither.
- **What the standard requires.**
  - [meta.reflection.result]/2-4: `reflect_constant(expr)` with `T`
    not a class type takes V as the value of `expr` and returns
    `template_arguments_of(^^TCls<V>)[0]`, a reflection of the value. With
    `T = std::meta::info` that is a reflection of the reflection value
    `m`, not a pointer to member function. The result is a function of
    the value alone.
  - [temp.inst]/4 and /5: a member of a class template specialization
    (or a function template specialization) is implicitly instantiated
    only when it is referenced in a context that requires its definition,
    or when the definition's existence affects the program's semantics.
  - [temp.inst]/8 and [expr.const.defns]/2.6: the definition affects
    semantics when the function is "needed for constant evaluation", that
    is, a constexpr function *named by* a potentially constant-evaluated
    expression.
  - [basic.def.odr]/3-4: a function is named by an expression when
    overload resolution performed as part of forming that potentially
    evaluated expression selects it. `members_of` names nothing. The
    operand of `^^` is an unevaluated operand ([expr.context]/1). Copying
    or re-reflecting an `info` value names no expression at all.
  - So nothing requires the instantiation. Only forming a pointer to the
    function (`extract` to a function pointer or pointer to member,
    `&[: m :]`, a splice in a call) odr-uses it. That path is WP-1244's
    `Sema::use_reflected_function` and is unchanged.
- **GCC 16.1 probes** (same file, `-DV=n`; errors counted). The body
  is the one above with `N = 2`. `first()` returns the operator from
  `members_of`, and `static_assert(first() == ^^Panel<2>::operator[])`
  holds in both compilers.
  - `reflect_constant(first())`: GCC 1, kiln 0.
  - `reflect_constant(^^Panel<2>::operator[])`: GCC 0, kiln 0.
  - `std::vector<info> v{^^Panel<2>::operator[]};
    reflect_constant(v[0])`: GCC 0, kiln 0.
  - Through a `members_of` vector: `reflect_constant(v[0])`,
    `reflect_constant_array(v)`, `define_static_array(v)` and
    `substitute(^^H, {reflect_constant(v[0])})` each give GCC 1, kiln 0.
    Holding the vector, `type_of`, and `Holder<^^Panel<2>::operator[]>`
    give GCC 0, kiln 0.
  GCC therefore gives two equal `info` values different behaviour by
  provenance, which the value-only specification rules out. This is a
  GCC 16.1 defect, not kiln's.
- **Tests.** `tests/conformance/meta.reflection.result/`
  `reflect-constant-info-no-instantiate.cpp`: the three shapes with a
  body whose static_assert fires if instantiated, checking that the
  results still reflect the right value (`is_value`, `extract<info>`,
  the array extent, the `define_static_array` span). It is kiln-only
  (`skip(clang)`) and `xfail(gcc)`, so a GCC that drops the instantiation
  shows up as an XPASS.
- **Deviations.** From GCC 16.1, deliberately, as above.
