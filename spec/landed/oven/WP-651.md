# WP-651 — Inline array step for pointer arithmetic in the Oven

No observable rule changes: pointer arithmetic gives the same pointer or
the same fault (kind, note text, the pointer and allocation it names) as
before, one-past-the-end included, and the pointer encoding and every
interface are unchanged. The `PtrAdd` aux gains a field (spec/oven.md
"Bytecode (KBC)", "Pointer steps"). This file records where the change
lives and the tests.

- **Problem.** Every `PtrAdd` called the outlined `Oven::ptr_add`
  (a large frame, its `Result` returned through memory). It found the
  allocation (`extent_of`, a full pointer decode), read the element
  type's size and kind and the allocation type's kind from the type
  table, compared the element types with `same_unqualified` (an
  outlined `same_class`), divided the offset by the element size and
  bounds-checked the index in `i128`. That was about 125 Ir per op,
  14% of `bench/oven/churn-vector`. Measurement:
  docs/status/perf-reflection.md "WP-651: pointer arithmetic".
- **Fix.**
  - `crates/kiln_oven/src/kbc.rs` `ptr_add_aux`: bits 10..=15 of
    `PtrAdd`'s aux hold the element size's shift plus one when the size
    is a power of two that can no longer change (the element is not an
    incomplete class's `Opaque` slot), else 0; also 0 for an unsigned
    128-bit index. `crates/kiln_oven/src/compile.rs` `emit_ptr_add`
    fills it at every `PtrAdd` the compiler emits.
  - `crates/kiln_oven/src/vm.rs`: `ptr_add_step` (always inlined into
    the `PtrAdd` arm) runs `ptr_add_array` when the field is nonzero:
    a zero index returns the pointer; otherwise the slot's allocation
    with the pointer's generation (`Memory::alloc_raw`, one match on the
    slot's class bits), its type an array of exactly the element type
    (`OTy` equality: operands are cv-unqualified), the current index
    `off >> shift`, the new index in `0..=n` by one `i128` compare, and
    the pointer rebuilt with `with_off` (past-the-end at `n`). Anything
    else returns `None` and the arm calls the cold `ptr_add_op`, which
    decodes the index as before and calls `ptr_add`. `ptr_add` (also
    used by the other callers) runs the same array step with the size
    read from the type table and a division, then `ptr_add_slow`, the
    pre-WP-651 body.
  - The arm writes the pointer register once from either path, so the
    fast path's result stays in a register.
- **Tests.** `vm.rs` unit test `ptr_add_agrees_with_the_reference`: the
  pre-WP-651 `ptr_add` is kept as the test's `ptr_add_reference`. For
  null, `NOWHERE` + 5, a function pointer, frame, heap and static
  allocations of scalars of sizes 0, 1, 3, 4, 8, 12 and 16, of arrays
  of 0, 1, 2, 5 and 7 of them and of a nested array, a dead frame slot,
  a flipped generation and missing slots in each space; at element
  offsets 0..=8, at offsets 1, `es` ± 1, the size ± 1 and 2^32 − 1,
  with and without the past-the-end bit; element types matching and
  not; indices −9..=9, ±2^40, `u32::MAX`, `i64` and `i128` extremes:
  `ptr_add` returns what the reference returns, and the inline step
  (both with the shift and with the size, negated and not) returns
  either `None` or the reference's pointer. The op's index decoding is
  checked for every width, signedness and negation. More than 100,000
  cases, `Ok`, `ArrayIndex`, `Mem` and `NullArith` all reached.
- **Bench.** `bench/oven/{churn-vector,sort-nohdr,table-nohdr,vector-alloc,wide-struct-read}.cpp`,
  S7 and S8 (`bench/reflect/`), `bench/frontend/templates_wide.cpp` and
  `accessor-wide-emit.cpp` (`-c -O2`); numbers are in
  docs/status/perf-reflection.md "WP-651: pointer arithmetic".
