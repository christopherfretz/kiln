# WP-1018 — The Oven: UB-check tails (parameter lifetime, volatile objects, reference members)

WP-948 left three gaps in the Oven's undefined-behaviour checks, each of
which accepted a constant expression that clang rejects. WP-1018 closes
them (it also covers WP-1019 and WP-1021). The checks and notes are in
spec/oven.md "Undefined behaviour checks".

- **Parameter objects end at the callee's return** (WP-1018,
  [expr.call]/7, implementation-defined; clang's `CallScope`). The caller
  keeps each by-value class argument's address below the call window and
  runs the new `Op::EndParam` after the call returns. A registered
  destructor runs then, last constructed first, and `Memory::kill` ends
  the allocation's lifetime (`Undo::Kill` restores it on rollback). The
  storage stays until the full-expression's scope releases it, so a
  pointer that escapes the call reads an "object outside its lifetime".
  `expr.const/call-out-of-lifetime.cpp` now passes.
- **Volatile locals, temporaries, heap objects and members** (WP-1019,
  [expr.const]/10.8). `TyInfo::has_volatile` and `FieldInfo::volatile`
  record volatile members. A frame or heap allocation whose type is
  volatile or holds one gets `flags::VOLATILE`. That is the static-only
  `MUTABLE_OUTSIDE` bit, which every load and store fast path already
  tests, so valid code pays nothing extra. `vm::volatile_path` follows
  clang's `findSubobject`:
  - only the accessed object's volatility counts;
  - the last volatile member on the path names the object;
  - an object whose constructor or destructor is running is not volatile.
  The complete object's own volatility is kept in
  `Oven::volatile_decls`/`volatile_exprs`, because interned types are
  cv-stripped. A write, compound assignment, increment or decrement
  through a volatile-qualified glvalue is a compile-time trap
  (`Compiler::volatile_glvalue`, clang `findCompleteObject`).
  `expr.const/read-volatile-local-and-heap.cpp` now passes.
- **Reference members** (WP-1021). At `-fclang-compat=22`, `Op::RefChk`
  also runs after a reference data member binds (`init_field`).
  Reference parameters and lambda init-captures stay unchecked, as in
  clang 22; clang 19 checks none of them. Both versions reject a
  reference constant result one past the end
  (`value::check_ref_past_end`, clang `CheckLValueConstantExpression`).
  kiln did not check this before at either level.

- `expr.const/ref-past-end-result.cpp`

xfail repro: `expr.const/initializer-reads-own-member.cpp`. In a
constexpr variable's initializer, the variable's name designates its
not-yet-live static allocation. It should designate the object under
construction, so reading an already-initialized member of it fails.

Known gaps, also in spec/oven.md:
- A pointer that escapes two call levels is noted "outside its lifetime"
  where clang says "variable whose lifetime has ended".
- The structor exemption matches the `this` offset only, so a base-class
  constructor at offset 0 also exempts the complete object.
- At level 19, kiln does not reject a new-expression of a class with a
  volatile member as non-literal.
