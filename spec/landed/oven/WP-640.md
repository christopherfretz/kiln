# WP-640 — glvalue immediate invocations and reference initializers

The rules are [expr.const]/16 and /22 (the result of a glvalue core
constant expression is the entity it designates), spec/oven.md "Nested
immediate invocations" and spec/reflection-values.md §5.2.

- **Cause.** Two layers lost the indirection of a reference result, so
  `extract<const T&>(^^obj)` (and any consteval function returning a
  reference) bound to the designated object's *value*:
  1. `Oven::compile_thunk` cached top-level thunks by expression alone.
     Sema's check of a variable's immediate invocations folds the whole
     initializer first (`try_fold`, value mode: a scalar glvalue is
     loaded); the later evaluation of `constexpr const int& r = …` as
     the initializer of `r` then reused that thunk, and `r` was frozen
     as the integer it read (IR `inttoptr (i64 21 to ptr)`, a run-time
     crash, `&r == &g` rejected).
  2. An immediate invocation's own evaluation (`EvalKind::Consteval`)
     froze a glvalue as its value too: it read the designated object, so
     one designating a non-const variable (`int& x = f();`,
     `extract<int&>(^^h)`) was rejected, and codegen ignored the stored
     value of a glvalue `ConstantExpr` and emitted the consteval call
     (an unsupported `CXXReflectExpr` under `-freflection`).
- **Fix.**
  - Thunks are keyed by `(expression, object, address mode)`
    (`Oven::thunks`, `thunks_at`): a reference variable's initializer
    binds its referent (`bind_ref`) whatever was folded before.
  - `Oven::evaluate` with `EvalKind::Consteval` and
    `Oven::fold_immediate_in` evaluate a glvalue in address mode: the
    thunk binds it as a reference initializer would and returns the
    address, frozen as a `Scalar::Pointer` of type `T&`
    (`SemaBridge::lvalue_ref_to`, implemented by sema's and codegen's
    bridges; a bridge returning `None` keeps value mode). The designated
    object is never read, and the result is checked as a permitted
    result like any reference.
  - A glvalue `ConstantExpr`'s stored value is therefore an address. The
    Oven's `rv_inner` never takes it as a value of the expression's
    type. In codegen, `emit_lvalue` lowers it as the constant address
    (clang `EmitLValue` of a `ConstantExpr` with an `APValue`), and the
    scalar, aggregate and complex emitters load or copy through that
    lvalue. Nothing calls the consteval function at run time.
  - `-ast-dump` prints no value for a glvalue `ConstantExpr`, as clang.
- **Tests.**
  - `tests/conformance/expr.const/immediate-invocation-glvalue-run.cpp`
    covers consteval functions returning `int&`, `const int&`, `int&&`
    and `P&`, with clang as the oracle (also agrees with GCC 16.1). It
    binds global, constexpr and local references; checks addresses in
    `static_assert` and at run time; copies a class result; and uses an
    invocation in a default argument.
  - `tests/conformance/meta.reflection.extract/references-run.cpp` and
    `references-gcc.cpp` (the same checks over libstdc++'s real
    `<meta>`, GCC 16.1 oracle) cover `extract<T&>` of:
    - variables, both const and non-const;
    - `reflect_object` of an element or a member;
    - `object_of` and `constant_of`;
    - class and array types;
    - an extracted reference read inside a larger constant expression
      and a template argument;
    - global, constexpr and local bindings.
  - The ill-formed `extract<int&>(^^g)` for a `const int g` stays in
    `extract-neg.cpp`.
- **Deviations.** None. `object_of` of a reference variable is still
  unimplemented ("kiln: object_of a reference variable is not
  implemented yet").
