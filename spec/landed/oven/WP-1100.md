# WP-1100 — The Oven: objects under construction (own-name reads, structor identity)

WP-1018 left two gaps in how the Oven treats an object under
construction. WP-1100 closes both (it also covers WP-1101). The rules
are in spec/oven.md "Evaluation entry points" and "Undefined behaviour
checks".

- **A variable's name in its own initializer** (WP-1100, [basic.life]/7,
  [class.cdtor]/2, [dcl.init.aggr]/7). `constexpr P p{1, p.x + 1};` was
  rejected: the name `p` resolved to the variable's static placeholder,
  which is not live yet, instead of the object being built. Now the
  aggregate thunk emits `Op::BindObject [p, global]` before it
  initializes its frame allocation. That sets the new
  `GState::Bound(p)`, so `Op::GlobalAddr` yields the object under
  construction, as clang's `EvaluatingDecl` does. This holds for static,
  constexpr and constexpr-local variables alike.
  - Naming a bound object bumps `run.impure`. Without that, a memoized
    call that reads the object would return a stale value after the
    object changes.
  - `eval_at` restores the previous state when its run ends.
    `Oven::unbound` lifts the binding while a nested evaluation runs
    (`run_job`, another variable's initializer).
  - Reading an element that is not initialized yet is still rejected,
    with clang's "read of object outside its lifetime"
    (`notes.rs` `unbegun_init_object`).
  - `expr.const/initializer-reads-own-member.cpp` (the WP-1018 xfail)
    now passes.
- **Structor exemption keyed on identity** (WP-1101, [class.ctor.general]/5,
  [class.dtor]/5). `vm::volatile_path` exempts an object whose
  constructor or destructor is running from the volatile check. It found
  that object by the `this` offset alone. A base subobject at offset 0
  shares that offset with its complete object, so re-constructing or
  destroying the base (`std::construct_at`/`destroy_at` on it) also
  exempted the rest of a volatile complete object. kiln accepted
  accesses there that clang 19 and 22 reject ("assignment to volatile
  object 'd' ...").
  - The exemption now matches both the offset and the class
    (`Func::this_ty`). No two live subobjects of one class share an
    address ([intro.object]/9), so the pair identifies the object.
  - An empty base at offset 0 is not in `Types::fields`, so the walk
    never enters it. Its constructor exempted the whole object before;
    now it exempts nothing else.
  - Const objects never used the offset rule: the `CONST` flag covers the
    whole allocation and is set only after initialization (`late_const`).
    clang 22 and kiln agree on `construct_at` of a const object's base.
    clang 19 words that case differently, so there is no corpus test.

Tests (tests/conformance):
- `expr.const/initializer-reads-own-member{,-local,-calls}.cpp`
- `expr.const/initializer-reads-unbegun-member.cpp`
- `class.ctor/constexpr-structor-volatile-{subobject{,-ok},empty-base}.cpp`

Perf: the walk runs only for allocations with `flags::VOLATILE`, and
`BindObject` is a cold op that runs once per aggregate variable
initializer. `cargo xtask bench --filter oven/` on the same host, before
and after: BENCH_PLACEHOLDER

Known gaps (wording only):
- A non-constexpr local that reads a later member in its own initializer
  (`P l{l.y, 2};`) is noted "uninitialized". clang says "outside its
  lifetime".
- A mem-initializer that reads a later member in a constexpr
  constructor is noted "uninitialized". clang says "outside its
  lifetime".
- An indeterminate member of an element that is already constructed
  (`{{}, p2.i.z}`) is noted "outside its lifetime". clang says
  "uninitialized".
- kiln does not give clang's `-Wuninitialized` "variable 'l' is
  uninitialized when used within its own initialization" for a member
  read (`constexpr P l{l.y, 2};`).
- A pointer to an empty base at offset 0 is printed as the first member
  (`&f.m`) in call notes. clang prints `&f`.
