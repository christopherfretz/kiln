# WP-1016 — LLVM toolchain discovery, LLVM 22 as the default backend, the runtime-dependency contract

1.0 work items A4 and Q6 (operator decision 11-08: kiln 1.0 supports LLVM
19 and 22, default 22).

## Discovery
- `crates/kiln_driver/src/llvm.rs` (spec/driver.md "LLVM discovery"):
  `SUPPORTED_LLVM_MAJORS = [22, 19]` (preference order; adding a major is
  one entry), `Search::run`. In order: `--llvm-dir=<dir>` (new flag,
  joined form, last wins), `$KILN_LLVM_DIR` (non-empty), the build's
  `KILN_DEFAULT_LLVM_DIR`, then per major (22's candidates before 19's):
  `llvm-config` (when its installation has that major) and
  `llvm-config-N` on `PATH`, the layouts `/usr/lib/llvm-N`,
  `/usr/lib64/llvmN`, Homebrew-on-Linux `llvm@N`/`llvm`, `/usr`, and
  `opt-N`/`clang++-N` on `PATH`. Prefixes come from resolving the tool's
  symlinks; nothing is spawned when `lib/clang/<N>` tells the major.
- Valid: `bin/opt`, `bin/llc`, `bin/clang++` and a supported major
  (`lib/clang/<N>`, else `bin/llvm-config --version` once per directory,
  else the directory name). An invalid or unsupported explicit choice is
  an error before anything runs (`drv_llvm_dir_invalid`,
  `drv_llvm_unsupported`), never a fall-through; invalid implicit
  candidates are skipped; nothing found is reported when a tool is first
  needed (`drv_llvm_not_found` with `drv_llvm_tried`,
  `drv_llvm_not_on_path` and `drv_llvm_install_hint` notes), so
  `-fsyntax-only`/`-E`/`-S -emit-llvm` work without LLVM.
- `Toolchain::new` takes the `--llvm-dir` value; `Toolchain::llvm` (a
  `LlvmSelection`) replaces `llvm_dir: String`, and `DEFAULT_LLVM_DIR`
  (`/usr/lib/llvm-19`) and the versioned-name-on-`PATH` tool fallback are
  gone (`Tool::name` is the plain name: `llc`, `clang++`). The
  `-print-prog-name=`/`-print-file-name=`/`-print-search-dirs` probes
  (WP-920) delegate to the selected `clang++`.

## Default pairing
- The default `-fclang-compat` stays 22, independent of the backend: the
  compat level is program semantics, the backend only the IR spelling
  (`llvm_major`); following the installed LLVM would change a program's
  meaning with the machine. Both cross pairings keep working.

## Visibility
- `--version` and `-v` add `LLVM backend: <major> (<dir>)` (or `LLVM
  backend: none (kiln supports LLVM 19 and 22)`) after `InstalledDir:`.
  The link-step `-v` passthrough is untouched.

## `-fp-contract` on x86 with LLVM 22
- LLVM 22's `llc` warns "X86 backend ignores --fp-contract setting; use
  IR fast-math flags instead." for x86 triples only (19 does not, nor do
  other 22 targets). `codegen_cmd.rs` no longer passes `-fp-contract=fast`
  when the target is x86 and the major is >= 22: kiln's IR already marks
  every FP operation `contract` under `-ffp-contract=fast` (as clang
  does), and `llc-22` output was byte-identical with and without the
  option (-O0/-O2, with and without FMA). Test `codegen.rs`
  `fp_contract_fast_backend_flag` (pinned to x86_64, both backends).

## Defaults that moved from 19 to 22
- Without `KILN_LLVM_DIR`, `cargo test` now drives LLVM 22 where it is
  installed. Tests that compare kiln with clang 19's IR name
  `--llvm-dir=/usr/lib/llvm-19`: `ir_vs_clang` (`KILN_LLVM_DIR` const,
  keeping its oracle-22 deviations' LLVM 19 premise), `codegen.rs`
  `coro_wrappers_before_passes_match_clang19`, `hardening.rs` (`both()`)
  and `driver.rs` `verbose_search_lists_match_clang`. The harness, the libc++
  runner and CI already export `KILN_LLVM_DIR=/usr/lib/llvm-N` per
  `KILN_ORACLE` (19 lanes explicit in `ci-lane.yml`), so no CI change.
