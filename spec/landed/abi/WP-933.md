# WP-933 — expression mangling, template-pattern `L`, pointer NTTP conversions

The rules below complete spec/abi.md §8.14 and §8.15. Each is compared
with clang 19 and clang 22 byte for byte: `tests/codegen/mangle_*.cpp`
(ir_vs_clang, both oracles and both triples) and
`tests/mangle/nttp_pointer_conversion.cpp` (mangle_vs_clang).

- **No silent placeholder for an unencodable expression** (WP-593). A
  template-argument expression, `decltype` operand or dependent array
  bound with no encoding used to mangle as `XLi0EE` / `u7unknown`, so two
  overloads that differed only there shared one symbol. It is now the
  error `cannot yet mangle expression type <ExprKind>` (diagnostic
  `cg_cannot_mangle_expression`, the one §8.16 uses for requires-clauses)
  at the innermost subexpression the mangler cannot encode
  (`Mangler::failed`); clang 19 and 22 reject the same forms
  (`__builtin_bit_cast`, `__builtin_offsetof`, `__builtin_choose_expr`,
  `__builtin_va_arg`) with the same text and location. kiln's caret has
  no source range. Test: `crates/kiln_driver/tests/codegen.rs`
  `unmangleable_expression_is_an_error`.
- **Expression forms added** (`mangle/dep.rs`, Itanium <expression> and
  <expr-primary>):
  - floating literal: `L <type> <hex of the IEEE bits> E`, most
    significant nibble first (`Ld3ff8000000000000E`, `Lf3fc00000E`); a
    primary expression, not wrapped in `X...E`;
  - string literal: `L <array type> E` (`LA4_KcE`), also primary;
  - `throw e` / `throw`: `tw <expression>` / `tr`;
  - `typeid(type)` / `typeid(expr)`: `ti <type>` / `te <expression>`;
  - temporaries: `MaterializeTemporaryExpr`, `CXXBindTemporaryExpr` and
    `ExprWithCleanups` are transparent (`skip_transparent`), so
    `S(x).v` is `dtcv1SfL0p_1v` and `S{x}.v` is `dttl1SfL0p_E1v`.
  - a braced-init-list operand (a call argument, `mn({1, V...})`):
    `il <expression>* E` (`_Z1gIiEDTclsr3stdE2mnilfp_fp_EEET_`;
    `tests/codegen/mangle_init_list_operand.cpp`).
- **Template-pattern `L`** (WP-603). The internal-linkage `L` of a
  function or variable template specialization's name follows its
  template's pattern (`template_l_prefix`): a `static` function template,
  a `static` variable template (and its explicit specializations,
  `_ZL2vtIlE`), and a closure in one (`_ZNKL2laIiEMUliE_clEi`). Members of
  an unnamed namespace keep `12_GLOBAL__N_1` and no `L`, as before. A
  non-`static` `const` variable template keeps external linkage
  (CWG2387; clang 19 and 22): `_Z3cvtIlE`, no `L`.
- **Closure linkage follows its variable.** A closure whose mangling
  context is a variable (a variable template's initializer) is externally
  visible only if that variable has external linkage (clang
  `getLVForClosureType`, ignoring the variable's own closure type); in a
  `static` variable template its members are `internal`, not
  `linkonce_odr`.
- **Pointer and reference NTTP conversions.** A pointer or reference
  template argument that names a whole object (no subobject path, not
  past the end) whose type is not the parameter's pointee (`int g` for
  `const int*`, `const volatile int&`) is wrapped in a conversion to the
  parameter type, as clang's `mangleTemplateArg` does for a
  `TemplateArgument::Declaration` whose type differs:
  `_Z5derefIXcvPKiadL_Z1gEEEiv`, `_Z2r1IXcvRKiL_Z1gEEEiv`. A matching
  type stays `XadL_Z1gEE` / `L_Z1gE`; a subobject or array element uses
  `so` (§8.14).
