# WP-1077 — linkage of closure types in function template signatures

WP-1060 left this open: a function template whose signature holds a
lambda was emitted `internal`, with its closures unnumbered (`$_N`),
where clang 19 and 22 use `linkonce_odr` and numbered closures. Two
units that formed the same specialization each had their own copy. The
rule is in spec/abi.md §8.15 and spec/sema-lambda.md §3.5.

## Forms compared with clang 19 and 22

| form | before | now |
|---|---|---|
| return type, `template<class T> auto ret(T) -> decltype([]{...})` | internal, `$_N` closure | `linkonce_odr`, `_ZZ3retT_ENKUlvE_clEv`; `ret<long>` `UlvE0_` |
| parameter type, `int par(T, decltype([]{...}) = {})` | internal | `linkonce_odr`, `_ZZ3parT_DTL3$_1EEENKUlvE_clEv` |
| NTTP type, `template<class T, decltype([]{...}) V = {}>` | internal, `_ZTA` object internal | `linkonce_odr`, `_ZTAXtlZ4nttpT_EUlvE_EE` |
| namespace member, `ns::ret` | internal | `linkonce_odr`, `_ZZN2ns3retET_ENKUlvE_clEv` |
| class template member, `S<T>::nret(T) -> decltype([]{...})` | internal, `$_N` | `linkonce_odr`, `_ZNK1SIiEUlvE1_clEv` |
| default template argument (namespace, class, global) | already as clang (WP-1062) | unchanged |
| NTTP default value, `auto V = []{...}` | already as clang | unchanged |

## Root cause

Deduction (`deduce_spec`) and `get_function_spec_signature` substitute
the signature in the template's context (namespace or class) with no
numbering state set, so `lambda_numbering_context` found no numbering
context and the closure had no number. An unnumbered closure has no
linkage (§8.9), and every specialization naming it became
unique-external, so `internal`. During a class template's
instantiation, a member's signature closure was likewise unnumbered.

## Fix

- kiln_sema `lambda/mod.rs`: `ManglingState.signature`, set by
  `begin_signature_mangling(tmpl, pattern)` and restored by
  `end_signature_mangling` (it also clears the variable, default
  argument and default template argument state for the duration). A
  closure created in the template's context is numbered in the pattern,
  which is its context declaration (clang runs `DeduceTemplateArguments`
  under `ContextRAII(pattern)`). A closure created in a class during
  that class's instantiation is numbered in the class, unless a
  variable of that class is being initialized; a variable elsewhere
  whose initializer triggered the instantiation does not count
  (`void *g = S<int>::nret(1)();`).
- kiln_sema `templ/deduce_call.rs` (`deduce_spec`) and `templ/funcs.rs`
  (`get_function_spec_signature`, numbering in the member template's
  own function for a class template specialization's member) set the
  state.
- kiln_abi `mangle.rs`: `closure_signature_fn` (the function a closure
  is numbered in). `effective_ctx` mangles the closure as that
  function's local entity. `tag_externally_visible` and
  `has_internal_linkage` give it the function's linkage.

## Tests

- `tests/codegen/lambda_in_function_signature.cpp`: the IR differential
  (linkage, names, comdats) on both triples.
- `tests/mangle/lambda_in_function_signature.cpp`: the clang 19 symbol
  differential.
- `tests/conformance/expr.prim.lambda.closure/lambda-in-signature-linkage-two-units-run.cpp`:
  two units form the same seven specializations. The closures' statics
  and the specializations' addresses are equal across the units (one
  definition each). Before the fix, every comparison printed 0.

## Left open (xfail repros)

- `lambda-in-signature-explicit-args-numbering-two-units-run.cpp`
  (explicit template arguments numbering a trailing return type's
  lambda twice, `ret2<int>` `UlvE0_`) was fixed by WP-1086; the rule is
  spec/sema-lambda.md §3.5.
- `lambda-in-signature-member-template-return-two-units-run.cpp`:
  instantiating `S<int>` substitutes its member template `mret`'s return
  type. Clang makes that closure never-dependent (unevaluated, in a
  non-dependent class: `TransformLambdaExpr`'s `LDK_NeverDependent`), so
  `S<int>::mret<int>` is `_ZN1SIiE4mretIiEENS0_UlvE_ET_`. Kiln's closure
  record is dependent (kiln_ast `builder.rs` `nested_in_template`: the
  member template's parameters are open), so `decltype` stays dependent
  and the name is `..DTLNS0_UlvE_EEET_`. Linkage is `linkonce_odr` in
  both.
