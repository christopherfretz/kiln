# WP-980 — libc++ 22 regressions on main: chrono mangling, mdspan, simd; narrow `++`/`--` in the Oven

The WP-961 sweep found libc++ 22 tests that passed in the WP-461 run
(docs/status/libcxx-m5.md) and failed on main. Each cluster was bisected
to the change that exposed it and fixed at its root. The rules live in
spec/abi.md §8.15–§8.16 (mangling), spec/sema-templates.md §7.2 (the
length sweep), spec/oven.md "Typed, checked arithmetic" and
spec/libcxx.md "Feature set".

## Chrono (22 std/time tests): temporaries in a requires-clause

- **Regressor:** 9cab5cf2e (WP-818, PR #383, merge 2d671d72a). It turned
  the `Qu7unknown` placeholder for an unencodable constraint into the
  error `cannot yet mangle expression type <kind>`. libc++ 22 constrains
  chrono's `operator<<` for `sys_time` with `_Duration{1} < days{1}`. The
  class prvalue bound to `operator<`'s reference parameter is a
  `MaterializeTemporaryExpr`, which the mangler never encoded.
- **Fix:** `mangle/dep.rs` `skip_transparent` skips
  `MaterializeTemporaryExpr`, `CXXBindTemporaryExpr` and
  `ExprWithCleanups`, as clang's `mangleExpression` does: a temporary
  mangles as the expression that creates it. WP-933 makes the same change
  independently, and its version is kept at the merge. Test:
  `tests/mangle/materialized_temporary.cpp`.

## Mangler audit: forms added, forms left

Every form below is checked against clang 19 and 22 symbol names in
`tests/mangle/expression_forms.cpp` (`mangle_vs_clang`). Floating and
string literals, braced lists, `throw`, `typeid` and field references
are WP-933's.

- **`delete`:** `delete e` is `dl <expr>`, `delete[] e` is `da <expr>`,
  and `::delete e` adds a `gs` prefix.
- **`__real__ e` and `__imag__ e`** mangle as the operand alone; clang
  has no operator name for them. kiln's parser drops `__extension__`
  entirely, so `decltype(__extension__ t)` mangles `Dt` where clang
  writes `DT`. That case is left as a follow-up.
- **Integer literals outside the signed 64-bit range**, such as
  `18446744073709551615ull`, keep their value as a constant:
  `Ly18446744073709551615E`.
- **Compound assignments** (`CompoundAssignOperator`) mangle as the
  binary operator they are, with the right operand read from the side
  record: `decltype(t += 1)` is `DTpLfp_Li1EE`.

The forms below still have no encoding. They are an error when they
occur in a signature: in a requires-clause since WP-818, and in a
template argument, a `decltype` operand or an array bound since WP-933.
- **clang also rejects these:** `ArrayTypeTraitExpr`; GNU `?:`
  (`BinaryConditionalOperator`); `ChooseExpr`; `CompoundLiteralExpr`;
  `VAArgExpr`; `BuiltinBitCastExpr`; `OffsetOfExpr`.
- **clang encodes these, but they are not seen in real signatures, so
  they are kept as errors:**
  - `ImaginaryLiteral` (clang writes `LCi0_2E`)
  - `UserDefinedLiteral` outside a call
  - `PackIndexingExpr` (clang 19 and 22 drop it, giving `DTE`, which is
    not followed)
  - `LambdaExpr`
  - `UnaryOp::Coawait`, `CoawaitExpr`, `DependentCoawaitExpr`,
    `CoyieldExpr` (coroutines are rejected, spec/oven.md)
  - `PredefinedExpr`, `SourceLocExpr`, `EmbedExpr`
- **Not dependent, or never written in a signature:**
  `SubstNonTypeTemplateParmPackExpr`, `FunctionParmPackExpr`,
  `CXXRewrittenBinaryOperator`, `ImplicitValueInitExpr`,
  `DesignatedInitExpr`, `DesignatedInitUpdateExpr`, `NoInitExpr`,
  `CXXInheritedCtorInitExpr`, `CXXDefaultArgExpr`, `CXXDefaultInitExpr`,
  `CXXParenListInitExpr`, `ArrayInitLoopExpr`, `ArrayInitIndexExpr`,
  `OpaqueValueExpr`, `StmtExpr`, `AddrLabelExpr`, `AtomicExpr`,
  `ShuffleVectorExpr`, `ConvertVectorExpr`, `ExtVectorElementExpr`,
  `RecoveryExpr`, `CXXExpansionSelectExpr`, `PseudoObjectExpr`.

## mdspan (5 tests): an empty function parameter pack in a generic lambda's fold

- **Regressor:** c8ce199c7 (WP-802, the empty-first-pack length sweep;
  PR #363, merge 69466d845).
- **The failing code:** libc++ 22's rank-0 `layout_right` and
  `layout_stride` mappings implement `operator()` with a generic lambda
  over `index_sequence<Pos...>`. Its fold names both the enclosing
  function's parameter pack `__idx` and the lambda's `Pos`.
- **How it broke:**
  1. Instantiating the enclosing function leaves `__idx` as a
     `FunctionParmPackExpr` (empty).
  2. `expr_packs` found no children under that node and fell back to
     walking its type, which is the pattern parameter's.
  3. That walk reported a pack of a retained level, so the sweep kept the
     expansion unexpanded.
  4. The Oven then failed with "constant evaluation of CXXFoldExpr",
     which surfaced as "static_assert not ICE" and the follow-on errors.
- **Fix:** `templ/pack.rs` `expr_packs` returns at a
  `FunctionParmPackExpr`, as it already does for a
  `SubstNonTypeTemplateParmPackExpr`. Test:
  `tests/conformance/temp.variadic/p7-empty-function-parameter-pack-in-generic-lambda-fold.cpp`.

## simd_unary: a flag kiln began to accept

- **Regressor:** 87f7d8f0f (WP-445, PR #189), which taught kiln
  `-flax-vector-conversions=`.
- **Why it passed before:** the WP-461 run was made at c14c90ac8, before
  WP-445 reached that branch. The libc++ runner passes
  `-flax-vector-conversions=none` (libc++'s `_warningFlags`), but only
  when the compiler accepts it, so kiln compiled the test with lax
  conversions.
- **Why it fails now:** `simd_unary.pass.cpp` writes
  `ADDITIONAL_COMPILE_FLAGS(clang): -flax-vector-conversions=integer`.
  It needs that flag because `vec_ext.h` `__negate` returns `!v`, a
  plain-`char` vector (clang `GetSignedVectorType`), into an
  `unsigned char` mask. That is an error under `none` in clang and in
  kiln alike, so kiln's behaviour was right.
- **Fix:** the runner applies `ADDITIONAL_COMPILE_FLAGS(clang)` flags to
  kiln, which implements clang's dialect (`features.rs`
  `DIALECT_FLAG_FEATURES`). `clang` stays out of the feature set for
  `XFAIL`, `UNSUPPORTED` and `REQUIRES`. Five libc++ 22 tests carry such
  a line: simd_unary, the two `time.zone.exception` `types.pass.cpp`
  (`-Wno-deprecated`) and the two `aliasing_iterator.pass.cpp`
  (`-Wprivate-header`).
- **Tests:** `directives.rs` `clang_dialect_flags`;
  `tests/conformance/ext.clang.vector_type/lax-none-logical-not-char-vector.cpp`
  and `lax-integer-logical-not-char-vector.cpp`.

## Oven: narrow signed `++`/`--` (stable_sort; was WP-981)

- **The bug:** `compile.rs` `inc_dec` added in the operand's own width.
  So `++` on a `signed char` holding 127 faulted with "value 128 is
  outside the range of representable values". clang promotes to `int`
  and wraps on the conversion back (`UnaryOperator::canOverflow` is
  false). This is not a regression: libc++ 22 `stable_sort.pass.cpp`
  (`test<char>()`) exposes it where plain `char` is signed.
- **Fix:** for a signed type narrower than 32 bits, `inc_dec` emits the
  add or subtract at 32 bits, then an `ICast` back to the narrow width.
  `bool`, enumerations and wider types are unchanged, and `int`/`long`
  `++` at the maximum still faults.
- **Tests:** `tests/conformance/expr.pre.incr/narrow-signed-wrap-constexpr.cpp`,
  `narrow-signed-wrap-plain-char.cpp` (`-fsigned-char`),
  `narrow-unsigned-wrap-plain-char.cpp` (`-funsigned-char`) and
  `int-overflow-constexpr.cpp`.
