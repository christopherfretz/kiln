# WP-583 — aarch64: aggregates are classified by their unadjusted alignment

- **Rule** (AAPCS64 §6.8.2 C.4, C.10; clang
  `AArch64ABIInfo::classifyArgumentType`). `aarch64_arg` reads the
  type's *unadjusted* (natural) alignment, `call::unadjusted_align(t, q)`
  over `Layouter::type_unadjusted_align` (spec/abi.md §5 step 5), not
  its layout alignment, in two places:
  - a non-HFA composite of at most 16 bytes is `i128` (an even register
    pair) when that alignment is 16, otherwise `[N x i64]`;
  - an HFA/HVA gets `alignstack(16)` when that alignment is at least 16,
    otherwise `alignstack(8)`.
- **What counts.** The record's own `alignas`/`aligned` does not, nor
  does an `aligned` typedef of it. A field's does (it raises
  `field_align`), and so does a field of an over-aligned class type,
  `__int128`, a 16-byte vector or a bit-field of an `__int128` type.
  `long double` is an HFA of `fp128` with `alignstack(16)`. `packed` and
  `#pragma pack` lower it. These are the results clang 19 and GCC 16.1
  give: `struct alignas(16) { long lo, hi; }` after an `int` is in x1:x2
  (`[2 x i64]`), not x2:x3.
- **Bases.** Clang 19/20 count only the fields; clang 21 on also counts
  each non-virtual base not placed as an empty base at offset 0
  (llvm-project#135551, not under `-fclang-abi-compat`). Kiln keys on
  `-fclang-compat >= 21`, so `struct DE : E { }` with an `__int128` in
  `E` is `[2 x i64]` at 19 and `i128` at 22.
- **Returns.** `aarch64_ret` keeps the layout (adjusted) alignment:
  clang 19 through 22 `classifyReturnType` reads `getTypeAlign`, so a
  returned `alignas(16)` pair is `i128` (x0:x1 either way).
- **`va_arg`.** `classify_va_arg` goes through `aarch64_arg`, and
  `aapcs_va_arg` (`kiln_codegen/src/va_arg.rs`) uses the unadjusted
  alignment for the general-register round-up, the stack round-up and
  the HFA temporary, as clang `EmitAAPCSVAArg` does.
- **x86-64** is unaffected except through the size: an `alignas(32)`
  struct of one `long` is 32 bytes, so MEMORY (`byval align 32`).
- **Tests.** `tests/codegen/overaligned_aggregate_args.cpp` (both
  triples, exact against clang 19 and 22 in `ir_vs_clang`: `alignas`,
  `aligned`, field `alignas`, nested, `__int128`, bit-field, union,
  `long double`, HFAs, packed, `#pragma pack`, typedef, bases, returns,
  `va_arg`); `tests/conformance/expr.call/
  ir-x86-64-overaligned-aggregate{,-19}.cpp`; the run tests
  `tests/conformance/expr.call/run-aarch64-overaligned-aggregate{,-gcc}.cpp`
  (`requires: target-aarch64`), whose other side of each call is
  assembly written to AAPCS64, since the harness has no multi-TU test.
- **Not done.** Clang 21+ lays an AArch64 bit-field wider than its type
  out in an `__int128` container (llvm-project#126774); kiln keeps the
  clang 19 `LayoutWideBitField` (spec/abi.md §5), so at
  `-fclang-compat=22` `struct { long c : 128; }` is 16/8 and
  `[2 x i64]` where clang 22 gives 16/16 and `i128`.
