# WP-694 — libc++ pass of the wave-1 projects

The M8 OSS harness (spec/landed/harness/WP-666.md) gains a libc++ mode,
and the ten wave-1 projects (fmt, nlohmann_json, range_v3, spdlog,
catch2, googletest, magic_enum, doctest, tl_expected, and cli11 as the
known-good check) build and test under it with kiln++ and the clang-19
control, both against the system libc++ 19. The results are the `libc++`
column and the "libc++ results (WP-694)" section of `docs/status/oss.md`,
plus a "libc++ (WP-694)" section on each project's page.

## Landed

- Harness libc++ mode, specified under "The C++ library (WP-694)" in
  spec/landed/harness/WP-666.md:
  - `oss-build.sh --stdlib libc++` (default `$KILN_OSS_STDLIB`).
  - `kiln-cxx` puts `-stdlib=libc++` before the project's arguments.
  - Build trees are `.oss/build/<project>/<compiler>-libcxx/` and
    `report.json` carries `"stdlib"`.
  - `oss-report.py --stdlib libc++` writes `<!-- oss:<project>:libcxx -->`
    blocks and the projects table's `libc++` column.
  - `scripts/oss/selftest.sh` covers the mode.
- `scripts/oss/projects.toml`: range_v3 configures with
  `-DRANGES_ENABLE_WERROR=OFF -DCMAKE_CXX_FLAGS=-Wno-deprecated-ofast`, as
  the WP-669 manual build did. Without them the clang-19 control fails every
  TU, because clang 19 deprecates range-v3's Release `-Ofast` and range-v3
  builds with `-Werror`.
- Results: all ten projects are at parity with the control on TUs, links
  and tests. range_v3 has 256/257 TUs, 254/255 links and 254/255 tests under
  both compilers. The shared failures are `test/view/tokenize.cpp` (libc++'s
  `regex_token_iterator` is not a forward iterator) and the `calendar`
  example link (the system Boost is built against libstdc++).
- Fix 1 ([class.default.ctor]/1). A constexpr constructor template that
  can be called with no arguments now counts as a constexpr default
  constructor in `has_constexpr_default_ctor`
  (crates/kiln_sema/src/class/special/implicit.rs; spec/sema-class.md).
  This matters at C++20 only; from C++23 an implicit constructor is
  constexpr anyway. It fixes fmt `test/ranges-test.cc` under libc++
  (`std::tuple` members). Test:
  `tests/conformance/class.default.ctor/constexpr-ctor-template.cpp`.
- Fix 2 ([over.match.copy]/1, [temp.deduct]). In a copy-initialization
  (no `ALLOW_EXPLICIT`), a non-dependently explicit constructor template
  is excluded before deduction and recorded as a non-viable `Explicit`
  candidate (`drop_explicit_ctor_templates` in
  crates/kiln_sema/src/overload/ics.rs; spec/sema-templates.md). This
  matches clang's `AddTemplateOverloadCandidate`. It fixes googletest
  `gmock-actions_test.cc`, where deducing libc++'s explicit
  `basic_string(const T&)` with a `void` argument formed a hard error. Test:
  `tests/conformance/over.match.copy/explicit-ctor-template-not-deduced.cpp`.
- Perf finding, logged reproducibly in `docs/status/oss.md`. Under libc++,
  kiln's wall time per TU is 1.1 to 1.9 times clang's while its RSS is 0.4
  to 0.8 times clang's. The gap is blocking file-system syscalls on the
  workspace bind mount (about 3000 waits per TU against about 600). On
  the container's own file system the two compilers take the same time.
