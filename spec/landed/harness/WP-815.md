# WP-815 — LLVM self-host: bootstrap stages in the OSS harness

M8 wave 4c. The clang 19.1.7 that kiln++ builds through the `llvm_clang`
row (stage 1, WP-801) builds the same LLVM tree again (stage 2), and the
stage-2 compiler runs check-clang and check-lld. A stage-2/stage-3 IR
comparison checks the same thing more cheaply. The results are in
docs/status/oss/llvm_selfhost.md.

## Landed

- `projects.toml` key `stage_of` (WP-815): the name of another cmake row
  whose build produced this row's compilers. `stage_cxx` and `stage_cc`
  (defaults `bin/clang++` and `bin/clang`) are their paths inside that
  row's build tree. `projects.py` refuses a `stage_of` that names the row
  itself, an unknown row, a non-cmake row or a row that is itself staged.
- `oss-build.sh` on a staged row takes the C++ compiler
  `.oss/build/<stage_of>/<compiler>/<stage_cxx>` and the C compiler
  `.oss/build/<stage_of>/<compiler>/<stage_cc>`, in place of kiln++ /
  `control_cxx` and `c_compiler`. So `--compiler kiln` means "with the
  compiler that kiln++ built", and `--compiler clang` means "with the one
  the control built". With `--stdlib libc++` (WP-694) they come from
  that row's `<compiler>-libcxx/` tree instead. `$KILN_OSS_CXX` is
  ignored. When either compiler is
  missing, it exits 2 and names the run that builds it. The wrapper
  (`kiln-cxx`) and the report are unchanged. A staged build's
  `compile.jsonl` therefore times the stage-1 compiler, and its `kind`
  rules apply to clang's diagnostics as they do for the control.
- `oss-build.sh --which` prints the resolved `CXX=` and `CC=` and exits 0
  before anything is cloned, configured or built.
- The `llvm_selfhost` row is the stage 2 of `llvm_clang`. It has the same
  tag, configure flags, build targets, test command and test timeout,
  `stage_of = "llvm_clang"`, and it shares that row's checkout
  (`checkout = "llvm_clang"`).
  - A separate row rather than a mode of `llvm_clang`: a mode would put
    two builds of one row in one `.oss/build/<row>/<compiler>/`
    directory, or need a third directory name that `oss-report.py`, the
    status table and the report schema do not know. A row reuses all of
    them unchanged. It also keeps stage 1's tree intact while stage 2
    builds from it.
- `scripts/oss/stage-diff.py` is the stage-2/stage-3 comparison.
  - `make --log <compile.jsonl> --sample N --out DIR NAME=CXX...` samples
    N of the log's `ok` build-phase TUs: sorted by absolute source path,
    every (count/N)-th. For each compiler it writes a `DIR/Makefile`
    target per TU that reruns the TU's own command with that compiler,
    with `-c`, `-o`, `-MD`, `-MMD`, `-MF`, `-MT` and `-MQ` dropped and
    `-S -emit-llvm -O2 -fdiscard-value-names -o DIR/NAME/<i>.ll` added.
    `--emit asm` drops `-emit-llvm` and writes `<i>.s`, which also
    compares the backend's output.
    Run the Makefile with `make -k` so it draws from the shared jobserver.
    `-fdiscard-value-names` is explicit because clang keeps value names by
    default only when it is built with assertions.
  - `compare --out DIR NAME...` compares each `<i>.ll` across the NAMEs
    (or `<i>.s`) after one normalization: the `!llvm.ident` string, or
    the assembly's `.ident` string, becomes `clang version`, since a
    vendor build such as Debian's names itself there. It prints a `DIFF` or `MISSING` line per TU and a summary, and
    writes each first difference to `DIR/diffs/<i>.diff`. It exits 1 when
    any TU differs or is missing.

## Tests

- `scripts/oss/selftest.sh`:
  - `stage_of` names a row, and `stage_cxx`/`stage_cc` take their
    defaults.
  - A `stage_of` that names itself, an unknown row, or a staged row is
    refused.
  - `--which` on `llvm_selfhost` over a fake `.oss` root, whose
    `build/llvm_clang/kiln/bin/clang++` and `clang` are links to clang 19,
    prints those two paths, even with `$KILN_OSS_CXX` set.
  - `--compiler clang --which` with no `build/llvm_clang/clang/` exits 2
    and says the compiler is not built.
  - `stage-diff.py` `make` and `compare` on a two-TU log, with two clang
    19 spellings, gives 2 identical.
- The self-host itself ran end to end (docs/status/oss/llvm_selfhost.md).
