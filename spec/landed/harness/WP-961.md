# WP-961 — the x86_64 confidence sweep

The libc++ 22 suite and the OSS corpus had only run on aarch64, the
development container's architecture. `.github/workflows/sweep.yml` runs
both on GitHub's x86_64 runners, never as a merge gate. The results and
the triage are in docs/status/x86_64-sweep.md; docs/VALIDATION.md "x86_64
sweep" says how to re-run it before a release.

## Landed

- `.github/workflows/sweep.yml`. Triggers: `workflow_dispatch` (boolean
  inputs `libcxx`, `oss`, `control`) and `push` to `sweep/**`; no
  `pull_request` or `merge_group` trigger, not a required check.
  Concurrency `sweep-<ref>` cancels a superseded run. Every job runs on
  `ubuntu-24.04` in the CI reference container `gcc:16.1.0-trixie`
  (ci-lane.yml's), through the existing `kiln-ci` composite action where
  Rust is needed; ci.yml and ci-lane.yml are unchanged.
  - `build`: `cargo xtask dist`, the archive (not `-symbols`) uploaded as
    `kiln-dist`. Every other job installs it into `/opt/kiln`.
  - `libcxx` ×6: libc++ 22 extracted into `.toolchain/libcxx-22-root`,
    the llvmorg-22.1.8 tests, the lit locales, then `cargo xtask libcxx std
    libcxx --tag llvmorg-22.1.8 --compiler /opt/kiln/bin/kiln++ --shard K/6
    --no-fail -j 4 --timeout 20 --mem-limit 3072 --results … --report …`
    (the aarch64 M5 invocation plus the shard). `libcxx-summary` merges
    the six results files with `scripts/libcxx-results.py` into the job
    summary.
  - `oss` (project × compiler): `scripts/oss/oss-build.sh <p> --compiler
    kiln|clang --jobs 4` on the runner's `/mnt`, the clang 19 control on
    an identical runner (dispatch input `control: false` skips it).
    `oss-summary` runs `scripts/oss/oss-report.py` over every report. A
    job with no report fails, and the summary lists every matrix pair
    without one (spec/landed/harness/WP-1241.md).
- `cargo xtask libcxx --shard K/N` (`Options::shard`, `parse_shard`,
  `shard_of`): round robin over the sorted selection, K − 1 modulo N;
  disjoint, covering. An empty shard is an error. `--results <file.tsv>`
  (`Options::results`, `results_tsv`): one tab-separated line per test
  (spec/libcxx.md "Results file").
- `scripts/libcxx-results.py`: merges results files (exit 2 on an
  overlapping test or a malformed line), prints the per-outcome counts for
  all / `std/` / `libcxx/` and the failing tests; `--baseline` marks each
  failure `new`, `same` or `absent` and lists the baseline-only failures.
- Tests: `libcxx::tests::shards_partition_the_selection`,
  `libcxx::tests::results_file_lines`, and `ci_tests::sweep_never_gates`
  (the triggers are exactly `workflow_dispatch` and `push` to `sweep/**`,
  no non-comment line names `pull_request` or `merge_group`, and every
  matrix project is a `scripts/oss/projects.toml` row).
- docs/VALIDATION.md "x86_64 sweep"; the release-candidate paragraph
  requires a sweep with no x86_64-only failure. docs/COMPATIBILITY.md
  "x86_64"; docs/status/x86_64-sweep.md.
- The shards write `libcxx-out/libcxx-K.{tsv,md}` in the workspace and
  upload that directory (an upload of a `runner.temp` path keeps the
  host's `__w/_temp` prefix inside the artifact); `libcxx-summary` finds
  the merged files with `find results -name 'libcxx-*.tsv'`.

## Fixed by the sweep (x86_64-only)

- Driver: `-mbranches-within-32B-boundaries` is accepted on x86 targets
  (clang's assembler padding option, no IR effect) and rejected elsewhere
  (spec/driver.md; `crates/kiln_driver/tests/hardening.rs`). Every
  daw_json_link TU passed it.
- Sema: `__rdtsc`, clang's plain x86 target builtin that ia32intrin.h's
  `_rdtsc()` expands to, resolves to the `__builtin_ia32_rdtsc` row
  (signature, codegen, target gating); spec/sema.md;
  `tests/conformance/target.x86/rdtsc-ir.cpp`, `rdtsc-not-aarch64.cpp`.

## Filed (xfail repros, follow-up WPs)

- `tests/conformance/target.x86/m-feature-flags.cpp`: x86
  `-m<feature>` / `-mno-<feature>` are unknown arguments (CMake SIMD
  probes in bitcoin_core and opencv turn code off).
- `tests/conformance/basic.extended.fp/float128-glibc-typedef-x86.cpp`:
  glibc's x86-64 `typedef __float128 _Float128;` is dropped, so
  `_Float128` and `__float128` functions differ (llvm_project `IRTests`).
- `tests/conformance/expr.pre.incr/narrow-signed-wrap-constexpr.cpp`
  (WP-981): constexpr `++`/`--` on a signed type narrower than `int`
  overflows instead of wrapping (libc++ `stable_sort.pass.cpp` with signed
  `char`).
