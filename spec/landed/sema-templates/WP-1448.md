# WP-1448 — explicit instantiation scope; recovery after tag and constraint errors; `used` members of class templates

- **Explicit instantiation scope.** An explicit instantiation whose name
  is qualified (a declarative nested-name-specifier) must inhabit a scope
  that contains the entity instantiated ([expr.prim.id.qual]/3): a
  namespace enclosing the innermost namespace of the template, or of the
  class template of a member. `check_explicit_inst_scope` (templ/spec.rs)
  runs for class, function and variable templates, member functions,
  member classes, static data members and member function templates
  (also constructor and conversion templates), as clang's
  `CheckExplicitInstantiationScope`: "explicit instantiation of 'E' not
  in a namespace enclosing 'N'" (`sema_explicit_inst_out_of_scope`), or
  "must occur at global scope" (`sema_explicit_inst_must_be_global`) for
  a template of the global namespace, each with the note "explicit
  instantiation refers here" at the template or member. The
  instantiation still takes effect. The generic qualified-declarator
  check ([dcl.meaning.general]/3) is not applied to an explicit
  instantiation. An unqualified name is checked only before C++23
  (C++20 [temp.explicit]/5: the template's namespace, or for an inline
  one a namespace of its enclosing namespace set;
  `sema_explicit_inst_unqualified_wrong_namespace`, "must occur in
  namespace 'N'"); P1787 dropped that sentence and the working draft has
  no replacement, so from C++23 kiln accepts it where clang and GCC do
  not (docs/status/deviations.md). An unqualified function name only
  finds what is nominable in the scope ([dcl.meaning.general]/3.3,
  unchanged). None of this applies in C++98 (WP-1473): C++98
  [temp.explicit]/5 named the template's own namespace, clang has only an
  off-by-default `-Wc++11-compat` warning there and GCC accepts, so
  `check_explicit_inst_scope` starts at C++11
  (`temp.explicit/enclosing-namespace-cxx98.cpp`).
- **Unsatisfied member, clang 22.** At `-fclang-compat=22` an explicit
  instantiation whose declarator matches a member function of a class
  template specialization whose trailing requires-clause is not
  satisfied is "no viable candidate for explicit instantiation of 'f'"
  (`sema_explicit_inst_no_candidate`), with "candidate function not
  viable: constraints not satisfied" and the satisfaction notes; clang
  19 instantiates the member.
- **Hard satisfaction errors.** A satisfaction check that failed by a
  diagnosed hard error ([temp.constr.atomic]/3: not `bool`, not a
  constant expression) leaves no record (`sat_hard_error`); a reference
  to the function is then not diagnosed again as "invalid reference to
  function: constraints not satisfied".
- **`used` member templates.** When a class template specialization is
  instantiated, each member function template whose pattern carries GNU
  `used` and has no definition is noted as used at the class's point of
  instantiation (`note_used_attr_members`, templ/class.rs), so it is
  diagnosed at the end of the unit (an inline one is
  `-Wundefined-inline`), as clang; non-template `used` members are
  referenced by WP-1430's `reference_used_members`. A `used` destructor of a class
  template is accepted: the attribute is not an odr-use and the
  exception specification is a complete-class context
  ([class.mem.general]/7); clang rejects it ("exception specification
  needed for member of incomplete class"), GCC accepts
  (docs/status/deviations.md).

Related sema changes of the WP (spec/sema.md rules they refine):

- **Typedef after a using-declaration.** A typedef-name declared after a
  using-declarator that named a typedef-name is checked as a typedef
  redefinition of the target ([namespace.udecl]/11,
  [basic.scope.scope]/4): the same type is valid, another type is
  "typedef redefinition with different types", and in a class any
  redeclaration is "redefinition of" ([class.mem.general]/6).
- **Elaborated reference to a typedef-name in a block.** The invalid
  recovery tag of `struct I` naming a typedef-name ([dcl.type.elab]/2)
  is pushed on the block scope, visible only to later
  elaborated-type-specifiers (`is_elab_only_local`), so a second
  `struct I` or `(struct I *)0` in the block is not diagnosed again; not
  when the typedef is declared in the same block. At namespace and
  class scope the recovery tag stays hidden (clang pushes it there too;
  follow-up).
- **Constructor recovery.** A constructor, destructor or conversion
  function declarator with a parameter of an unknown type is invalid,
  so no "constructor cannot be redeclared" follows; a class made invalid
  by an invalid member gets no implicit member initialization, so no
  "must explicitly initialize the reference member" follows.
