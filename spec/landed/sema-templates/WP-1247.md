# WP-1247 — a failed static_assert in a lambda body does not stop the evaluation

Downstream finding K2. The rule is in spec/sema-templates.md
§5.5, the "A lambda body that reports its own error" paragraph.

The repro (synthetic, 18 lines; `-std=c++26`, libstdc++ 16.1 for
`<stdexcept>`, `<string>` and `<span>`): `rules_v<T>` is a variable
template initialized by an immediately invoked lambda
`[] -> std::span<const int> { static_assert(sizeof(T) == 0, "...FIRST_REFUSAL..."); return {}; }()`.
`bind_site<Widget>()` iterates `rules_v<Widget>`, then calls a consteval
function that throws an exception whose `what()` is
`widget: SECOND_REFUSAL_SHOULD_BE_PRINTED`; `static_assert(bind_site<Widget>());`.

- **GCC 16.1** (the downstream oracle), three error lines:
  - `9:29: error: static assertion failed: widget: FIRST_REFUSAL (a static_assert)`
  - `18:32: error: non-constant condition for static assertion`
  - `18:32: error: uncaught exception of type 'refusal'; 'what()': 'widget: SECOND_REFUSAL_SHOULD_BE_PRINTED'`
- **clang 22** (and clang 19, identical), 2 errors: the static_assert
  failure with its "while substituting into a lambda expression here" and
  instantiation notes, then `18:15: error: static assertion expression is
  not an integral constant expression` with `5:54: note: subexpression not
  valid in a constant expression` at the `throw` (clang implements no
  P3068), so clang also evaluates past the failed assertion.
- **kiln 1.0.0**, 2 errors: the static_assert failure (as clang), then
  `18:15: error: static assertion expression is not an integral constant
  expression` with no note. The second refusal was lost.
- **kiln after this WP**, 2 errors: the static_assert failure, then the
  same error with `5:54: note: unhandled exception: widget:
  SECOND_REFUSAL_SHOULD_BE_PRINTED`. GCC's last two error lines are
  kiln's error and note (kiln's established form for an uncaught
  exception, spec/oven.md), so the diagnostics match GCC's one for one.

Cause: `Substituter::lambda_expr` (templ/subst/lambda.rs) failed the
lambda-expression whenever its body reported an error of its own. A
failed `static_assert` counted as one, so the substituted lambda was
discarded (`act_on_lambda_error`), `rules_v<Widget>`'s initializer
became an error, and the read of it in `bind_site` ended the evaluation
silently. clang only fails the lambda for an invalid body, and
`BuildStaticAssertDeclaration` returns a (failed) declaration.

Fix: `InstState::static_assert_errors` counts the errors reported while
checking a substituted `static_assert` (`Substituter::static_assert_decl`,
less those of a body its evaluation instantiated), and `lambda_expr`
does not count them as the body's own. A function definition
instantiation restores the counter (its errors are already in
`body_errors`), so nothing is counted twice. Only the lambda path
changes: in a function body a failed `static_assert` was already no
statement error. Nothing new is diagnosed: a variable template whose
initializer itself fails (`T::missing`) already kept the evaluation
going, and a non-constant read of a specialization whose initializer
did not evaluate still ends it, as GCC and clang do.

Not changed: a class template whose member `static_assert` fails stops
its instantiation (clang `InstantiateClass`, test
`temp.inst/failed-static-assert-stops-instantiation.cpp`), so a later
member access is a "no member named" error; GCC instead goes on to the
uncaught exception. kiln follows clang there.

Tests (tests/conformance/temp.inst/):
`failed-static-assert-lambda-keeps-evaluating.cpp` (P3068, kiln only:
the reported shape without the standard headers, a lambda made and one
called in a function template),
`failed-variable-template-init-keeps-evaluating.cpp` (P3068, kiln only:
plain variable template initializers),
`failed-static-assert-lambda-next-error.cpp` (the same shapes with a
non-constexpr call as the second error; clang 19 and 22 agree).
