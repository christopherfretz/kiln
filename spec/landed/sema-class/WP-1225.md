# WP-1225 — literal closure types

A 1.0 blocker from the pre-RC OSS pass: at C++17 and C++20 a constexpr function returning a lambda with a capture (a third-party library's `static constexpr auto F(T&& from) { return [&from](...) {...}; }`) was rejected with "constexpr function's return type '(lambda at ...)' is not a literal type". The contract is spec/sema-class.md §4.6 (`LITERAL`). Every behaviour below matches clang++-19 and clang++-22.

- Root cause: `class/special/implicit.rs` `special_member_bits` made a class literal only when it is an aggregate or has a constexpr non-copy/move constructor or a trivial default constructor. A closure with a capture is none of these, so it was never literal. WP-1123 (51a49f8fd) added the pre-C++23 literal return/parameter check, which exposed it. A captureless closure was literal even before C++17.
- Fix: a closure type is literal from C++17 when its destructor and members are, with no constructor needed, and never before C++17 (clang `CXXRecordDecl::isLiteral`). This covers the return and parameter rule, constexpr variables, and the Oven's `CheckLiteralType`.
- `class/members.rs` `with_non_literal_notes`: before C++17 the first note is `note_non_literal_lambda`, "lambda closure types are non-literal types before C++17". From C++17 a non-literal closure gets the "no constexpr constructors" note, as in clang, which the old code skipped. The class is named as its type, `'(lambda at F:L:C)'`; it used to print as `''`.
- Tests: `tests/conformance/expr.prim.lambda.closure/p3-literal-closure-cxx{14,17,20,23}.cpp` and `p3-literal-closure-cxx17-run.cpp`.
