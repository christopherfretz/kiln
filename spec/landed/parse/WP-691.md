# WP-691 — simdjson v4.2.4: GNU fallthrough null statements, alignas of an injected-class-name, u8 literals before C++20

Found building simdjson v4.2.4 with kiln++ (docs/status/oss/simdjson.md).
Each behaviour below was reduced to a standalone program that clang++-19
accepts (or diagnoses identically), and is pinned by a conformance test
that also passes under clang++-19. No miscompile was found: the arm64
(NEON) kernels are built and selected, and every runtime test passes.

## Behaviour

- **GNU attributes on a null statement** ([stmt.pre]/1,
  [dcl.attr.fallthrough]/1; spec/parse.md, attribute placement). A
  statement that begins with one or more GNU `__attribute__((...))`
  specifiers directly followed by `;` is an attributed null statement in
  every language mode, as in clang's
  `ParseStatementOrDeclarationAfterAttributes`. So
  `__attribute__((fallthrough));` marks a fall-through like
  `[[fallthrough]];` and needs no C++17-extension warning. kiln used to
  parse it as a declaration and report "expected expression". GNU
  attributes followed by anything else still start a declaration or an
  expression statement, as before.
  Test: `tests/conformance/dcl.attr.fallthrough/gnu-attribute-null-stmt-cxx11.cpp`.
- **`alignas(type-id)` with an injected-class-name** ([dcl.align]/1,
  [temp.local]/1; spec/parse.md, `alignas`). The operand of `alignas` is
  classified with the tentative type-id test that `sizeof(...)` uses
  (clang `ParseAlignArgument`, `isTypeIdInParens`). Inside a class
  template, its injected-class-name used without a template argument
  list therefore names the current specialization, and
  `alignas(GenericValue)` is an alignment of that type. kiln used to
  read it as an expression and report "'GenericValue' does not refer to
  a value" (rapidjson `document.h`).
  Test: `tests/conformance/dcl.align/alignas-injected-class-name.cpp`.
- **UTF-8 string literals before C++20** (C++17 [lex.string]/8, C++20
  [lex.string]/6 and P0482R6, [lex.ext]/5; spec/sema-conv.md,
  `string_literal_elem`). Before C++20 a `u8"..."` literal is an array
  of `const char`; from C++20 it is an array of `const char8_t`. The
  argument of a literal operator for `u8"..."_x` has the same element
  type. kiln used to type `u8` string literals as `char8_t` in every
  mode, so simdjson's C++17 `u8"..."_padded` found no
  `operator""_padded(const char *, size_t)`. `u8` character literals
  already followed `-std`.
  Tests: `tests/conformance/lex.string/utf8-literal-char-pre-cxx20.cpp`,
  `tests/conformance/lex.string/utf8-literal-char-cxx20.cpp`.

## Not in scope

- `-Wuninitialized` for a local read before any assignment (simdjson's
  `iterate_char_star_should_not_compile`). This needs the
  uninitialized-values flow analysis (WP-443 UNINIT-a,
  docs/design/uninitialized-values.md).
- `-fchar8_t` / `-fno-char8_t`. The `u8` element type follows only
  `-std`.
