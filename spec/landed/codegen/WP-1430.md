# WP-1430 — `used` members of implicit instantiations; parse-time emission order

Follow-ups of WP-1425, found in downstream code. Every rule below is
clang's (19 and 22 alike) and is pinned by an IR test equal to clang's.

## `used` member functions of implicit instantiations

- **Rule** (clang `TemplateDeclInstantiator::VisitCXXMethodDecl`,
  "PR17480: Honor the used attribute to instantiate member function
  definitions"): when a class template specialization or a member class
  of one is instantiated, each non-template member function whose
  instantiated declaration carries GNU `used` (`__attribute__((used))`,
  `[[gnu::used]]`, also with `retain`; constructors, destructors and
  conversion functions included) is referenced
  (`MarkFunctionReferenced`) at the class's point of instantiation. Its
  definition is therefore instantiated at the end of the translation
  unit, an ill-formed body is diagnosed with the "in instantiation of
  member function ... requested here" note at that point, and it is
  emitted `linkonce_odr` (internal in an unnamed namespace, `hidden`
  under `-fvisibility=hidden`) and listed in `@llvm.compiler.used`
  (`@llvm.used` too with `retain`). Not referenced: a member function
  template (clang marks its templated declaration, which only gives a
  `-Wundefined-inline` warning kiln does not reproduce), a friend
  function, a static data member (in-class `inline` or out of line), a
  member of a member class that is not itself instantiated, a member
  whose `used` is written only on its out-of-line definition (the
  instantiated declaration is the in-class one). Under an explicit
  instantiation declaration the definition is instantiated but not
  emitted (`available_externally`, only when optimizing).
- **Sema**: `Sema::reference_used_members`, called by
  `Substituter::class_body_with` once the class is complete (clang does
  it while declaring each member; there a `used` destructor fails with
  "exception specification needed for member of incomplete class", a
  clang defect kiln does not reproduce).
- **Codegen**: an implicit instantiation that `DeclMustBeEmitted` waits
  in `to_emit` (clang `MayBeEmittedEagerly` is false for one: a later
  explicit instantiation could change its linkage), functions and
  structors alike (`emit_global_fn`, `emit_global_structor`). A `used`
  structor is emitted like a `used` function (it was dropped).
- **Attributes of an instantiation**: `@llvm.compiler.used` /
  `@llvm.used` membership and a variable's must-emit test read the
  attribute through the pattern (`Ast::inherited_attr`): a `used`
  variable template's specialization, a static data member or member
  function whose `used` is on the out-of-line definition. The C1 / D2
  aliases of a `used` structor are listed too (clang
  `emitConstructorDestructorAlias` → `SetCommonAttributes`).
- **Non-template classes** (also explicit specializations): an in-class
  `used` definition (member function, structor, friend, nested class's
  member) is emitted right after the class's static data members, in
  member order (clang `HandleInlineFunctionDefinition` defers it to the
  end of the class's `HandleTopLevelDecl`); it was not emitted at all
  (`Cg::emit_used_inline_defs`).

## Parse-time handovers inside a top-level block

- **Rule**: clang hands a namespace, linkage specification or export
  block to `HandleTopLevelDecl` when it is closed, and emits its
  declarations then (`EmitDeclContext`). The definitions Sema hands over
  while parsing it come first: an explicit instantiation definition's
  members (`InstantiateClassMembers`, `InstantiateFunctionDefinition`),
  and a variable instantiated at a reference
  (`InstantiateVariableDefinition`'s `PassToConsumerRAII`). So every
  explicit instantiation written in a top-level block, nested blocks
  included, is emitted before the block's first declaration, in source
  order; a reopened block is a new top-level declaration.
- **Codegen**: `Cg::emit_parse_time_defs` walks a top-level block before
  `emit_members` does and hands over, in member order, the
  `explicit_member_insts` keys, the `ref_var_insts` keys and the
  explicit instantiation definitions listed in the block: classes
  (`Cg::listed_explicit_class`), functions and variable templates
  (`Cg::listed_explicit_fn_or_var`). Each key is handed over once and
  the listed ones are remembered (`parse_time_handed`), so the walk that
  follows skips them. At the translation unit's own level nothing
  changes: each top-level declaration is its own handover.
- **Static data members**: the instantiated out-of-line definition of a
  static data member is listed in the block of its pattern's definition.
  clang emits it at the explicit instantiation instead: with its
  class's members, or where `template int C<long>::m;` is written. Sema
  now keys the latter in `explicit_member_insts`
  (`act_on_explicit_var_inst`), and the walk skips both
  (`Cg::explicit_inst_member_def`). kiln emitted it before the pattern's
  block's other declarations, even for an explicit instantiation at
  the translation unit's level.

## Vtable order

- **Rule** (clang `DefineUsedVTables` walks `VTableUses` in the order
  the uses were recorded): the vtable of a class with a key function is
  used where the key function is defined, that of an explicitly
  instantiated class at the explicit instantiation; both kinds are
  defined in one order. kiln emitted all key-function vtables first.
- **Codegen**: `explicit_vtables` records each class with its position
  (`Cg::explicit_position`: the declaration the explicit instantiation
  follows, the last declaration of a block it follows, or the block or
  translation unit it starts; an implicit declaration, such as the
  global `operator delete` a virtual destructor declares, is passed
  over, `Cg::prev_position`), and `emit_key_function_vtables` sorts
  both kinds together by declaration number, a key function's class
  first at a tie.

## Not done

- A `used` constructor of an implicitly instantiated dynamic class: its
  virtual functions are created (declared) before the constructor in
  clang, because Sema's `HandleVTable` defines the vtable while the
  constructor's definition still waits in `DeferredDeclsToEmit`; kiln
  defines the vtable when the constructor references it. The emitted
  definitions and `@llvm.compiler.used` are equal, only the function
  order differs.
- The `-g` `DISubprogram` declaration line of an explicitly specialized
  member (debug info, another work package).
