# WP-971 — ICE audit: kiln_codegen and kiln_pp panic sites (covers WP-973)

Every `expect`, `unwrap`, `unreachable!`, `panic!` and `assert!` (including
`debug_assert*`) outside `#[cfg(test)]` in kiln_codegen `class.rs`,
`expr.rs`, `stmt.rs`, `complex.rs`, `cleanup.rs`, `fir.rs` and kiln_pp
`preprocessor.rs`, `ifeval.rs` was triaged:

- **(a) internal**: an invariant that Sema, the parser or the emitter
  itself guarantees. The panic stays, and its message now names that
  invariant.
- **(b) user-reachable**: reached with a crafted TU. It is fixed at the
  root, the way clang does it, rather than turned into a "cannot compile"
  error. Each one has a regression test that crashed before the fix and
  a valid twin that passes.

## Where the (a) invariants come from

- **Sema typing.** Messages "Sema: …" and "Sema typed it _Complex". Codegen
  runs only when `error_count() == 0`, so every expression has been typed
  and checked, and every declaration has been resolved and completed.
  Error-recovery ASTs never reach codegen.
- **Insertion point**, `fir::OPEN_BLOCK` (25 sites).
  - `emit_stmt` skips a statement in unreachable code unless it contains a
    label (spec/codegen.md §4).
  - Declarations, VLA bounds, `noreturn` calls and throw-expressions reopen
    a block with `ensure_insert_point`, as clang's `EnsureInsertPoint`
    does.
  - The two (b) sites below were holes in this invariant.
- **Emitter bookkeeping.** Messages such as "set for a dtor body",
  "emit_switch set f.sw", "a cleanup was pushed", "placed once",
  "placeholder {n} resolved by finish" and "%{n} defined before use". These
  are state the same function set up earlier on the same path.
- **Local checks.** Messages "match guard checked it", "is_none() returned
  above", "caller checked: …" and "sret, Ignore handled above". In each,
  the condition is tested a few lines earlier.
- **Preprocessor.** "top is a file/macro" and "i is a file" refer to the
  kind of the include-stack entry. The caller just matched or pushed that
  entry. Malformed directives are diagnosed before these sites, and no
  probe reached them. `ifeval.rs:651` is guarded by `precedence()`, which
  admits only binary operators.

## Reached and fixed

- **`fir.rs:970`, a push with no insertion point.**
  - A declaration after a `noreturn` call or a throw-expression stored its
    NRVO flag before reopening a block. A VLA's bound computation had the
    same fault.
  - `emit_one_var_decl` (expr.rs) and `emit_vla_bounds` (vla.rs) now call
    `ensure_insert_point` first, matching clang's `EmitAutoVarAlloca` and
    `EmitVariablyModifiedType`.
  - Tests: `tests/conformance/class.copy.elision/nrvo-candidate-after-noreturn-run.cpp`
    and `tests/conformance/dcl.array/vla-after-noreturn-run.cpp`.
- **`cleanup.rs:618`, `pop_catch` with a cleanup still on top.**
  - When a coroutine's initial `await_resume()` returns a result with a
    non-trivial destructor, that result's cleanup was pushed inside the
    initial-suspend catch-all and was never popped.
  - The discarded result is now emitted in its own scope (coro.rs).
  - The assert also changed from `debug_assert!` to `assert!`, so a violation
    is an ICE in release builds too.
  - Test: `tests/conformance/dcl.fct.def.coroutine/initial-await-resume-nontrivial-result.cpp`.

The sweep also reached three faults outside the audited files.

- **kiln_abi `irtype.rs:639`, "overlapping IR members".**
  - A bit-field access unit could run into a virtual base's storage.
  - Bit-field access units are now clipped at clang's
    `calculateTailClippingOffset`: the smallest offset of a virtual base
    that is not empty and is not a nearly-empty base without its own
    storage. The clip applies to the complete type only.
  - Test: `tests/conformance/class.bit/bitfield-access-unit-vbase-tail-run.cpp`.
  - Release builds, where the `debug_assert!` is off, went on without the
    check.
- **kiln_sema `conv/soft.rs:327`, arithmetic overflow.**
  - A hex float literal with a huge exponent overflowed in `round_rational`.
    The sum now saturates, so the literal becomes inf or 0 with clang's
    warning.
  - Test: `tests/conformance/lex.fcon/hex-float-huge-exponent-run.cpp`.
- **kiln_pp `directive.rs`, include cycle (a hang, not a panic).**
  - A file that includes itself along two paths never terminated, because
    every branch re-ran until it hit the depth limit.
  - Once "#include nested too deeply" has been emitted,
    `Preprocessor::include_limit_reached` stops kiln from re-entering any
    file it has already entered. This is clang's
    `HasReachedMaxIncludeDepth`.
  - The depth check now runs after the include guard and `#pragma once`
    skips, as in clang, so kiln reports the same single error.
  - Tests: `tests/conformance/cpp.include/include-cycle-two-back-edges.cpp`
    and its twin, `include-cycle-bounded-run.cpp`.

## Fuzz sweep

The runner was a script around kiln++ with a 20 s timeout per file. It
reported PANIC (ICE banner) and TIMEOUT. The input was the clang 22.1.8
test files.

- **Before**, on base 13e45f942.
  - Input: CodeGenCXX and CodeGenCoroutines, 1262 files, `-emit-llvm`.
  - 3 panics: irtype.rs, fir.rs and cleanup.rs, all above.
  - 2 timeouts: `mangle-ms-back-references-pr13207.cpp` and
    `pr29160.cpp`.
- **After.**
  - Input: CXX, SemaCXX, SemaTemplate, Parser, CodeGenCXX and
    CodeGenCoroutines, 4050 files. Run once with default flags, and the
    codegen directories again with `-O1 -g -fno-exceptions`.
  - Result: 0 panics. The same 2 timeouts remain.
- **Preprocessor** (Preprocessor and Lexer, 512 files, `-E` and
  `-fsyntax-only`).
  - kiln_pp panics: 0 before and after.
  - The 1 Sema panic (soft.rs) is fixed, and so is the `include-cycle.c`
    hang.
  - `bigoutput.c` still times out.
