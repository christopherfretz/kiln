# WP-1365 — `-g`: imported entities

The sister project hod found with its debug-info comparison that kiln
emitted no `DIImportedEntity`: a debugger could not resolve a name the
source reaches through `using namespace N;`, `using N::x;` or `namespace
A = N;` (gdb and lldb look names up through `DW_TAG_imported_module` and
`DW_TAG_imported_declaration` inside namespaces and functions). clang 19
and 22 emit them, identically for every case below.

## Rule

With reduced debug information (any `-g` kind above line tables only,
clang `hasReducedDebugInfo`) kiln follows clang's `EmitUsingDirective`,
`EmitUsingDecl`, `EmitUsingShadowDecl` and `EmitNamespaceAlias`
(`debuginfo/imported.rs`), at clang's emission points: the top-level walk
(`emit_member`, clang `EmitTopLevelDecl`; namespaces, linkage
specifications and export blocks are walked, classes are not) and a
`DeclStmt` of a function body being emitted (clang `EmitDecl`, also after
a `return`; a statement clang skips, a discarded `if constexpr` branch or the
branch of a constant-false `if`, is not). A declaration of an
imported named-module unit is not (clang hands it no top-level
declaration).

- **Scope.** At namespace scope: the enclosing namespace's `DINamespace`,
  else the compile unit (a linkage specification or export block is no
  scope; clang `getContextDescriptor`). At block scope: the innermost
  lexical block, else the subprogram (clang `LexicalBlockStack.back()`).
- **Where kept.** A namespace-scope entity goes to the compile unit's
  `imports:` in emission order; a block-scope one to its subprogram's
  `retainedNodes`, in creation order with the variables kept there when
  optimizing (LLVM 19 and 22's `DIBuilder` tracks local imported entities
  per subprogram). An identical entity (same tag, name, scope, entity,
  file and line) is kept once (`DIBuilder`'s uniquing check).
- **Using-directive.** `DW_TAG_imported_module` of the nominated namespace
  (through aliases); nothing for an anonymous namespace (its implicit
  using-directive). The line is that of the declaration's name.
- **Namespace alias.** `DW_TAG_imported_declaration` named after the
  alias, of the namespace; an alias of an alias imports the first alias's
  entity (cached per alias, clang `NamespaceAliasCache`).
- **Using-declaration.** One `DW_TAG_imported_declaration`, for the first
  of its shadows in clang's order (the most recently first-declared entity
  first) that is not a function whose return type is still to be deduced
  where clang emits the declaration ("debuggers can detect that this is
  an overloaded name"). Its entity: a type's `DIType` (class, enum,
  typedef, alias), a function's distinct definition `DISubprogram` when
  the unit emits one (before or after the using-declaration), else a
  uniqued declaration (`spFlags: 0`, no `unit`, no `scopeLine`; clang
  `getFunctionForwardDeclaration` and `finalize`'s `FwdDeclReplaceMap`),
  a variable's definition `DIGlobalVariable`, else a declaration
  (`isDefinition: false`, `isLocal` for internal linkage). A shadow naming
  a function or class template, a variable template, an enumerator
  (also every shadow of `using enum`) or anything else emits nothing and
  ends the search. Unresolved (dependent) using-declarations emit nothing;
  in an instantiated function body the instantiated declaration is
  emitted. A using-declaration of a shadow names the shadowed entity.
- **Deduced return types.** clang emits a namespace-scope
  using-declaration when its top-level declaration ends, and a block-scope
  one when its function is emitted (at the end of the unit for an
  inline, internal or instantiated function). kiln approximates "deduced
  by then" by declaration order: the function's definition precedes the
  using-declaration, or (block scope) the enclosing function's body is
  deferred and the function is defined anywhere in the unit.
- **Module imports.** clang emits a `DIModule` for `import M;` only when
  tuning for lldb (`-glldb`); at its default (gdb tuning on Linux) it emits
  nothing, and neither does kiln. In a module interface unit kiln emits
  the namespace-scope entities as clang 22 does (and clang 19 for a `.cpp`
  interface); clang 19's driver compiles a `.cppm` through its BMI and
  then emits only the block-scope ones.
- **Line tables only.** At `-gline-tables-only` / `-g1` (also optimized)
  nothing of the above is emitted, and the compile unit (`emissionKind:
  LineTablesOnly`) carries no `globals:`, `retainedTypes:`, `enums:` or
  `imports:` and no `#dbg_declare` / `#dbg_value` (llc 22 rejects that
  shape). This already held; the WP pins it with a test.

## Tests

- `tests/codegen/debug_imported_namespace.cpp`: namespace-scope
  using-directives (in the unit, a namespace, a linkage specification;
  naming an alias), aliases and aliases of aliases, an inline namespace,
  the anonymous namespace.
- `tests/codegen/debug_imported_decls.cpp`: using-declarations of
  variables (defined, declared only, defined later, internal), functions
  (overloads, declared only, defined later, a template last, noreturn,
  variadic, deduced and undeduced `auto`), types, enumerators, `using
  enum`, a class template, a shadow of a shadow.
- `tests/codegen/debug_imported_local.cpp`: block scope in nested lexical
  blocks, a function template instantiation, an inline function, a lambda,
  after a `return`; `debug_imported_o1.cpp` the `retainedNodes` order when
  optimizing.
- `tests/codegen/debug_imported_line_tables.cpp` (`-gline-tables-only`)
  and `kiln_driver`'s `line_tables_only_has_no_variables` (the same unit
  at `-gline-tables-only`, `-g1`, `-O1`, `-O2` and `-g -gline-tables-only`:
  none of the lists or records).
- All `ir_vs_clang` cases are byte-exact against clang 19 and, before
  structural normalization, also equal clang 22's output (aarch64 and
  x86_64).
- `tests/debuginfo/imported_entities.cpp`: gdb and lldb print a variable
  through a using-directive in a namespace and at block scope, call
  through a block-scope using-declaration, and print through a block-scope
  and a namespace-scope alias.
