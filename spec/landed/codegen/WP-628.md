# WP-628 — NEON load/store, lane, splat, permute and arithmetic builtins

The second NEON table in `neon.rs` ([`shape`]), next to WP-558's bf16
intrinsic table (spec/landed/codegen/WP-558.md "bf16 lowering"). Each
builtin lowers to the plain IR clang 19's `EmitAArch64BuiltinExpr` /
`EmitCommonNeonBuiltinExpr` emits for it; `clang -O0 -S -emit-llvm` is
the oracle.

## NEON load/store builtins

**Type code.** A `_v` builtin's trailing immediate selects `VTy` as clang
`NeonTypeFlags` / `GetNeonType` (AArch64): bits 0-3 the element (Int8 0,
Int16 1, Int32 2, Int64 3, Poly8 4, Poly16 5, Poly64 6, Poly128 7,
Float16 8, Float32 9, Float64 10, BFloat16 11; poly elements are
integers, Poly128 is `<16 x i8>` either way), `0x10` unsigned, `0x20`
quad (128 bits, else 64). Any other code is the codegen error "invalid
type code for `<name>`". A `_bf16` builtin is its `_v` twin (clang
`NEONEquivalentIntrinsicMap`). The type code and every lane/shift
immediate are folded at codegen (fold prepass: `builtins::folded_args`
lists `neon::imm_args`), as clang's `EmitScalarOrConstFoldImmArg`.

**Alignment rule.** A load or store through the builtin's pointer
operand `p` uses `p`'s known alignment (clang `EmitPointerWithAlignment`
on the argument before its conversion to `const void *`; kiln
`pointer_and_align`): the element's natural alignment for a plain
element pointer (`align 1` for 8-bit elements, 2 for `f16`, 4 for
`s32`/`f32`, 8 for 64-bit elements), more when the pointee or the
declaration says so. It is not always `align 1`: clang 19 emits `align 4`
for `vld1q_s32(const int32_t *)`.

**Results.** A result keeps `VTy` (or the element type): clang returns it
unconverted and the header's conversion to the user type is a bitcast or
nothing (as WP-558's `bfdot`). Operands are emitted left to right, then
bitcast to `VTy`.

| Builtin | IR |
|---|---|
| `vld1[q]_v`, `vld1[q]_bf16` | `load VTy, ptr p, align A` |
| `vst1[q]_v` | `store (bitcast v to VTy), ptr p, align A` |
| `vld1[q]_lane_v` | `insertelement (bitcast v), (load elt, ptr p, align A), i32 lane` |
| `vst1[q]_lane_v` | `store (extractelement (bitcast v), i32 lane), ptr p, align A` |
| `vld1[q]_dup_v` | `insertelement poison, (load elt), i32 0`, then `shufflevector` with a zero mask |
| `vldrq_p128` / `vstrq_p128` | `load`/`store i128, align 16` |
| `vget[q]_lane_<t>`, `vdup<b,h,s,d>_lane[q]_<t>` | `extractelement (bitcast v to <t vector>), i32 lane` |
| `vset[q]_lane_<t>` | `insertelement (bitcast v), x, i32 lane` |
| `splat_lane_v`, `splatq_laneq_v`, `splatq_lane_v`, `splat_laneq_v` | `shufflevector v, v, splat(lane)`; the result has VTy's lanes, twice that, or half that |
| `vmovn_v` | `trunc (bitcast v to <N x 2E>) to VTy` |
| `vext[q]_v` | `shufflevector a, b, <n, n+1, …, n+N-1>` |
| `vzip[q]_v`, `vuzp[q]_v`, `vtrn[q]_v` | for `i` in 0, 1: `gep inbounds VTy, ptr p, i32 i`, the shuffle, `store` at VTy's ABI alignment (zip: `(j + iN)/2` and `+N`; uzp: `2j + i`; trn: `j + i`, `j + N + i` for even `j`) |
| `vshr[q]_n_v` | `lshr` (unsigned code) / `ashr` by a constant splat; a shift by the element width is `zeroinitializer` (unsigned) or a shift by width - 1 (signed) |
| `vqtbl1_v`, `vqtbl1q_v` | `llvm.aarch64.neon.tbl1.v8i8` / `.v16i8` (WP-558's intrinsic table) |

`vshr[q]_n_v` and the builtins of "NEON arithmetic builtins" below are
arithmetic (WP-586's scope); they are here because the reference
workload's scanner, hash and linear-algebra translation units reach them,
and with them every builtin an `arm_neon.h` intrinsic reaches (each of
the header's intrinsics compiles at -O0 alone), except the families
below.

The `_x2`/`_x3`/`_x4` loads and stores are not lowered yet (no builtin
shape); `vld2`..`vld4`/`vst2`..`vst4` are (WP-803, below), their
`arm_neon.h` macros being statement expressions with a class result.

## NEON arithmetic builtins

The builtins below lower as clang 19 `EmitAArch64BuiltinExpr` /
`AArch64SIMDIntrinsicMap`, for every element type the type code allows.
`VTy` and the `_f16` twins are as above (`vmax_f16` is `vmax_v`, code 8
or 40). Operands are emitted left to right, then bitcast to `VTy`; a type
code of the wrong class (a float code for `vqsub`, an integer one for
`vsqrt`, any `bf16` code) is "invalid type code for `<name>`".

**Elementwise calls** (`neon.rs` `call`). Intrinsic `<base>.<VTy>` with
the operands in order; target intrinsics are `nocallback nofree nosync
nounwind willreturn memory(none)`, the generic `llvm.fabs`/`llvm.sqrt`/
`llvm.fma`, `llvm.trunc`/`ceil`/`floor`/`roundeven`/`round`,
`llvm.ctpop`/`ctlz` also `speculatable`. A poly code (`vcnt_p8`) is the
signed column. "Declared" results are bitcast to the
builtin's declared type (`<8 x i8>`/`<16 x i8>`); the others keep `VTy`.

| `vshl_v`, `vrshl_v`, `vqshl_v`, `vqrshl_v` (+ q; a, count; WP-803) | `aarch64.neon.{s,u}shl`, `{s,u}rshl`, `{s,u}qshl`, `{s,u}qrshl` by the signed per-lane count, bitcast to and from the declared type |
| `vdot{,q}_{s,u}32` (r, a, b; WP-803; also `vdot{,q}_lane{,q}_{s,u}32` through `splat`) | `aarch64.neon.{s,u}dot.v{2,4}i32.v{8,16}i8` of the accumulator and the two byte vectors, the result returned as is (clang `EmitCommonNeonBuiltinExpr`); needs the `dotprod` feature |

A shift or lane immediate out of range is "invalid shift for `<name>`" /
"invalid lane for `<name>`" (a diagnostic, not a panic). A non-`laneq`
`vfma` lane is bounded by the two-`c` shuffle (`2 * |S|`), as clang's
sema bounds it by `VTy` (`vfmaq_lane_f64` accepts lane 1).

## Tests

- tests/conformance/target.neon/ir-load-store-19.cpp: IR, clang < 22.
- tests/conformance/target.neon/ir-lane-permute-19.cpp: IR, clang < 22.
- tests/conformance/target.neon/load-store-run.cpp: run, -O0, against
  scalar code.
- tests/conformance/target.neon/lane-permute-run.cpp: run, -O2, against
  scalar code, including an 8-byte control-group match.
- tests/conformance/target.neon/ir-arith-19.cpp: IR, clang < 22, every
  little-endian `arm_neon.h` wrapper of the arithmetic builtins above
  (`-march=armv8.2-a+fp16+aes`).
- tests/conformance/target.neon/arith-run.cpp: run, -O0, against scalar
  code.
- tests/conformance/target.neon/ir-arith2-19.cpp: IR, clang < 22, every
  little-endian `arm_neon.h` wrapper of the shift, narrow/widen, by-lane,
  width-conversion and second-table call builtins, plus full-width shifts
  (`-march=armv8.3-a+fp16`).
- tests/conformance/target.neon/arith2-run.cpp: run, -O0, against scalar
  code.
- `neon.rs` unit tests `type_codes`, `shapes`, `perm_masks`.

The IR tests pin clang 19: clang 22's `arm_neon.h` wraps every builtin in
`__builtin_bit_cast` and a `__ret` temporary, so its IR differs around
the builtins, not in them. All AArch64-only (`requires: target-aarch64`,
no `--target`); they skip on x86_64.
