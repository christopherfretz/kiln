# WP-633 — trial-fold an automatic aggregate only when its value can be used

## Symptom

A class with N accessor member functions, each bound by a lambda wrapper
through a class-template `def` chain whose call thunk holds the whole
class by value in a `std::tuple` local, took 70 s to emit IR at N = 1600
(clang 19 takes 6.5 s on the same input). The emit time grew as N^2.6.

## Root cause

The codegen fold pre-pass (`Collect::var`, crates/kiln_codegen/src/fold.rs)
trial-folded the initializer of every automatic array or record. For each
thunk, the Oven built the N-member object, and each member store did a
linear subobject scan. The total was O(N^3). Codegen used the result only for a
POD aggregate (`Cg::emit_var_init`, clang `IsConstantAggregate`), and
`Oven::destroy_var` read it only for a `const` variable. The folds of
non-POD, non-`const` aggregates did nothing.

## Rule

An automatic variable whose initializer is not a constant initializer is
folded only when it is a reference, or an array or record that is `const`
or POD (`crate::class::is_pod`: trivially copyable, trivial default
constructor, standard layout, looking through array types). The emitted IR
is unchanged.

The driver now prints the module after the AST and the Oven are dropped. On
the -O2 path, it moves the frontend's IR text into the first `opt` run
instead of cloning it (crates/kiln_driver/src/codegen_cmd.rs `lower`,
`execute`). These are spec/driver.md internals and do not change
behaviour.

## Tests

- `tests/codegen/local_aggregate_nonpod.cpp` covers POD, non-POD (an NSDMI
  and a user destructor), array, empty-list, and `const` and non-`const`
  constexpr-destructor locals. Its IR matches clang 19 and 22
  (`ir_vs_clang`).
- `bench/frontend/accessor-wide-emit.cpp` is the shape above at 400
  members (3.3 s before, 2.0 s after). Its record is in
  `bench/baselines/frontend.json`.
- The measurements are in docs/status/perf-reflection.md,
  "`synth_accessor_god` production TU (WP-633)".
