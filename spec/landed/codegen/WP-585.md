# WP-585 — GNU inline functions are not externally visible (the -O1 `strchr` hang)

## Symptom

A header-only OBJ/MTL loader's material parser, compiled by kiln, hung
at -O1 and lost map entries at -O2, while -O0 and clang were correct.
The standard (`-std=c++20`/`c++26`), the standard library (libstdc++
or libc++) and `-ftrivial-auto-var-init` made no difference.

## Root cause

kiln did not know the GNU `gnu_inline` attribute (it was an unknown
attribute, ignored with a warning). Under `__OPTIMIZE__` (any `-O1`+)
glibc's `<string.h>` declares, for C++, an optimized-only overload:

```cpp
extern "C++" const char *strchr(const char *s, int c) __asm("strchr");
__extern_always_inline const char *strchr(const char *s, int c) {
  return __builtin_strchr(s, c);
}
// __extern_always_inline = extern __inline
//   __attribute__((__always_inline__, __gnu_inline__))
```

In C++, clang treats every `gnu_inline` definition as not externally
visible (`isInlineDefinitionExternallyVisible` is false, so
`basicGVALinkageForFunction` gives `GVA_AvailableExternally`), and
`shouldEmitFunction` then drops this one, since it is trivially
recursive (its body calls `__builtin_strchr`, the builtin form of its
own label). The call becomes a call to the C library's `strchr`.

kiln instead emitted the overload as an ordinary inline function:
`define linkonce_odr ptr @strchr(...)` whose body,
`__builtin_strchr` lowered to a call of `@strchr`, calls itself. That
definition replaced the C library's `strchr` in the program. LLVM
then turned the self tail call into an infinite loop at -O1, and at
-O2 (an infinite side-effect-free recursion in a `mustprogress`
function is undefined) folded the callers' results away, so the
parser's "is there a space after the key" test went the wrong way and
the unknown-parameter entry was never inserted. At -O0 the overload is
not declared at all (no `__OPTIMIZE__`), so -O0 was correct. Without
LLVM passes the same IR overflows the stack.

## Minimal repro

```cpp
#include <cstdio>
extern "C++" const char *find_byte(const char *s, int c) __asm("strchr");
extern __inline __attribute__((__always_inline__, __gnu_inline__))
const char *find_byte(const char *s, int c) { return __builtin_strchr(s, c); }
int main(int argc, char **) {
  char line[] = "key hello world";
  line[0] = char('k' + argc - 1);
  const char *sp = find_byte(line, ' ');
  std::printf("key=%d rest=[%s]\n", int(sp - line), sp + 1);
}
```

Before the fix: -O1 never terminates, -O2 exits without output. After:
`key=3 rest=[hello world]` at every level, as with clang.

## Fix

- Sema (`decl.rs`, `decl_attrs.rs`): `gnu_inline` / `__gnu_inline__` /
  `gnu::gnu_inline` is `AttrKind::GNU_INLINE`, with clang's checks
  (`handleGNUInlineAttr`): only on functions, ignored on a function not
  declared `inline` (`sema_gnu_inline_requires_inline`,
  -Wignored-attributes), warned without `extern`
  (`sema_gnu_inline_cpp_without_extern`,
  -Wgnu-inline-cpp-without-extern). spec/sema.md "GNU inline
  functions".
- Codegen (`module.rs`): an external-linkage function with
  `GNU_INLINE` is "defined elsewhere" (`Cg::defined_elsewhere`), the
  same state as a function under an explicit instantiation
  declaration: emitted `available_externally` when
  `keeps_available_externally` holds (`always_inline` at -O0, any
  non-`noinline` at -O1+, never when trivially recursive), else only
  declared. spec/codegen.md "GNU inline functions".
- Codegen (`recursion.rs`): `is_trivially_recursive` names an
  unmangled function by its plain name when it has no asm label (clang
  `isTriviallyRecursive`), so the C spelling of the same overload
  (`extern inline __attribute__((gnu_inline)) char *strchr(...)` with C
  linkage) is also recognised.

The IR for the shapes in `tests/codegen/gnu_inline.cpp` (-O0) and
`tests/codegen/gnu_inline_o1.cpp` (-O1: asm-labelled and recursive,
`extern inline`, `always_inline`, `noinline`, a function template, a
static member, an in-class member, `constexpr`, `static`, unnamed
namespace) is identical to clang 19's on aarch64 and x86_64.
