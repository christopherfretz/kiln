# WP-1372 — `-g`: vtable homing of dynamic class types

The sister project hod found with its debugger harness that kiln, at
`-g`, described a dynamic class in a namespace with no key function as an
incomplete type: gdb printed `<incomplete type>` for `*this` inside an
override, with `llc` as the back end too, while clang's output was
complete. The class was a `DIFlagFwdDecl` declaration because
`di_omit` (`debuginfo/types.rs`) left every dynamic class to its vtable,
and nothing completed it when the vtable was emitted: `di_home_class(rd,
false)` had no caller (WP-1323 item 1).

## Rule

At the reduced kinds (`-g`'s default `Constructor` and
`-fno-standalone-debug`'s `Limited`) kiln follows clang 19 and 22's
`shouldOmitDefinition` and `completeClassData` on Linux:

- A dynamic class (one with a vtable) gets its full `DICompositeType`
  (elements, `vtableHolder`, `DW_TAG_inheritance` with `DIFlagVirtual`
  for a virtual base, the `_vptr$X` member) exactly in a unit that
  defines its vtable: the key function is defined here (`external`
  vtable), the class has no key function and its `linkonce_odr` vtable is
  used here (a constructor is emitted), or it is a template
  specialization whose vtable is emitted (implicit or explicit
  instantiation). `emit_vtable_def_as` (`vtable.rs`) calls
  `di_home_class(rd, false)` before the VTT and the vtable's initializer,
  clang `GenerateClassData`.
- A construction vtable in a VTT also completes its base subobject's
  class (`emit_vtt`, clang `GenerateConstructionVTable`), so a template
  base with a virtual base whose own vtable is not emitted here is still
  a definition.
- An `available_externally` vtable (above `-O0`, for an explicit
  instantiation declaration) completes nothing: clang 19 and 22 keep the
  declaration.
- Anywhere else a dynamic class stays a `DIFlagFwdDecl` declaration: the
  key function is defined in another unit, or the class has no key
  function and nothing here emits its vtable (it is only used through
  pointers or references).
- A dynamic class whose vtable has LLVM `external` linkage, defined here
  or not, has no `identifier:` (clang `needsTypeIdentifier`): kiln
  dropped it only for a declared vtable, which never showed while such a
  class was never completed.

`-fstandalone-debug` (`Full`) and `[[clang::standalone_debug]]` still
emit every class completely; without `-g` nothing changes.

## Tests

- `tests/codegen/debug_vtable_home_ns.cpp`: the reported shape (an
  override of an inline virtual function in a namespace) and a class with
  a virtual base, no key function.
- `tests/codegen/debug_vtable_key_fn.cpp`: key function defined here
  (also with a virtual base), key function defined elsewhere, no key
  function and no vtable here.
- `tests/codegen/debug_vtable_template.cpp`: class template
  specializations with a virtual base, one completed only by a
  construction vtable.
- All three are byte-exact against clang 19 (`ir_vs_clang`, aarch64 and
  x86_64) and structurally equal under clang 22.
- `tests/debuginfo/vtable_home.cpp`: gdb `print *this` and `ptype` in an
  override and in a method of a class with a virtual base show the
  members, as does lldb's `frame variable *this` (kiln, clang 19 and
  clang 22).
