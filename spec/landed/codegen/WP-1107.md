# WP-1107 — Coverage fidelity: zero-record order and `(bool)new T` (also WP-1108)

The contract is spec/codegen.md §5.4 "Instrumentation" (records) and §3
(the fold prepass). These were the two differences from clang that
[WP-1082](WP-1082.md) (its WP-1083 part) left open. With them fixed,
kiln's `__llvm_covmap`, `__llvm_covfun` and `__llvm_coverage_names` are
clang's, byte for byte, on the corpus below.

## WP-1107: the order of zero records

**What clang orders by.** clang keeps one insertion-ordered map,
`CodeGenModule::DeferredEmptyCoverageMappingDecls` (a `MapVector`).
- `AddDeferredUnusedCoverageMapping(D)` does `try_emplace(D, true)`, so
  the first deferral fixes the position.
- `ClearUnusedCoverageMapping(D)` (called when D is emitted) sets the
  entry to false in place. For an instantiation it first clears the
  pattern.
- `EmitDeferredUnusedCoverageMappings` walks the map at the end of the
  TU and writes a zero record for each entry still true.

Entries are added in three places:
1. `CodeGenModule::EmitTopLevelDecl` adds a function or method
   definition the parser met at namespace scope.
2. `CodeGeneratorImpl::HandleInlineFunctionDefinition` (ModuleBuilder.cpp)
   adds an inline member definition. Only `Sema::ActOnFinishInlineFunctionDef`
   calls it, so it covers parsed definitions only. It is skipped in a
   dependent lexical context.
3. `Sema::InstantiateFunctionDefinition` (SemaTemplateInstantiateDecl.cpp)
   ends with `Consumer.HandleTopLevelDecl`. That runs before its own
   local and global pending instantiations are performed, so nested
   instantiations come in depth-first pre-order. Most of them run in
   `PerformPendingInstantiations` at the end of the TU.

**Root cause.** WP-1083 guessed the problem was instantiation time. It
was not: kiln's sema already instantiates when clang does
(`note_used_for_instantiation` / `drain_pending_instantiations`), and
`cov_defer_insts` already follows (3).

The real bug was in `cov_defer_class`, which implements (2). It walked
every class in the TU, including class template specializations
(`extern template struct S<long>;`, implicit instantiations). It
deferred their members as if the parser had finished them, so a
specialization member's record took the class's position. In clang
that member gets its position later, when its instantiation ends.

**Fix.** `crates/kiln_codegen/src/coverage/records.rs:198`: in
`cov_defer_class`, skip a member that `Ast::instantiated_from` marks
as instantiated.

In `tests/codegen/trivially_recursive.cpp` at `-O1`, kiln used to put
`sfun`'s record first. clang orders them `gfun`, `gfun2`, `strlen`,
`sfun`, and kiln now does too.

## WP-1108: `(bool)new T` in codegen folds

**Where clang folds.** Coverage uses `CoverageMappingBuilder::ConditionFoldsToBool`
(`EvaluateAsBooleanCondition`). Codegen uses `CodeGenFunction::ConstantFoldsToSimpleInteger`
in `EmitIfStmt`, `EmitBranchOnBoolExpr`, `?:`, `&&`, `||` and `!`. Both
evaluate outside a constant context.

`PointerExprEvaluator::VisitCXXNewExpr` (ExprConstant.cpp) succeeds when
both of these hold:
- the allocation function is a replaceable global one
  (`isReplaceableGlobalAllocationFunction`), the nothrow form with its
  one placement argument, or the reserved placement form;
- the initializer evaluates.

The allocation then stays live. `CheckMemoryLeaks` is only a `CCEDiag`
there, so `EvaluateAsRValue` still succeeds as long as the value does
not point at the heap. The consequences:
- `if (new int(4))` emits no allocation.
- `c || new int(4)` loses the right-hand branch counter.
- `static bool b = new int;` is the constant `true`.

**Fix.** The Oven gains a codegen-only knob, `Oven::set_fold_leaks`
(`crates/kiln_oven/src/lib.rs:730`). With it set, the outermost
evaluation of a fold outside a constant context accepts live
allocations. The check is in `crates/kiln_oven/src/value.rs:263`.
The fold prepass sets it next to `set_fold_float_ub`
(`crates/kiln_codegen/src/fold.rs:153`, cleared at :230).

Everything else keeps [expr.const]/5.20:
- constant expressions;
- sema's evaluations;
- calls' memoized results (`eval_subst`, `eval_call`).

The existing `fold_rvalue` path already supplies the rest of clang's
behaviour:
- a class-specific or user placement `operator new`, a runtime array
  bound, a non-constexpr constructor or a non-constant initializer does
  not fold;
- a value that points at the allocation (`int *p = new int`) does not
  fold.

## Remaining difference (follow-up)

- The bool conversion of a placement new into a global
  (`new (&glob) int(3)` as a condition) is `icmp ne ptr @glob, null` in
  kiln. clang's IRBuilder folds it to `true` (LLVM's `ConstantFolder`:
  a non-weak global is never null). The AST fold is not involved,
  since writing `glob` is not constant. The comparison builder is
  `crates/kiln_codegen/src/func.rs:2124` (`FuncGen::icmp`), which folds
  only integer constants.
