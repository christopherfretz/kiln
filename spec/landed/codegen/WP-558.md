# WP-558 — arm_neon.h bf16 builtins

AArch64 per-function target features, clang's emit-time
`checkTargetFeatures`, and the bf16 NEON lowering. The sema half (the
builtin table, `__has_builtin`, `neon_vector_type`, `target("...")`
parsing) is spec/landed/sema/WP-558.md.

## Target features

### Feature map

A function's feature map (`target_features.rs` `feature_map`, clang
`getFunctionFeatureMap`) is built in three steps:

1. Start from the base set: `fp-armv8`, `neon`, `outline-atomics` (per
   `-m[no-]outline-atomics`), `v8a`, and `-fmv`.
2. Apply `CodegenOptions::target_features`, the command line's resolved
   features (spec/codegen.md §7aa).
3. Apply the function's `target("...")` features.

The `"target-features"` attribute of a function with `target("...")`
prints that map.

### `target("...")` features

The driver parses the string through the hook
`CodegenOptions::target_attr` (a `TargetAttrParser`), and codegen applies
the result. The parser is `kiln_driver::features::target_attr_features`,
the model of clang 19 / 22 `AArch64TargetInfo::parseTargetAttr` plus
`initFeatureMap`. It works in two steps.

**Seeding.** An LLVM `ExtensionSet` is seeded from the module's
features: each extension feature is touched and set to on or off (LLVM
`reconstructFromParsedFeatures`).

**Items.** Each comma-separated item is then handled in order:

| Item | Effect |
|---|---|
| `arch=`, `cpu=`, `tune=`, `branch-protection=`, `+x`, an empty item | Skipped. |
| `no-X` or `noX`, where `X` is a `-march=` extension name (`nosimd`, `nobf16`) | Disables `X` in the set, cascading to what depends on it. |
| An extension name (`bf16`, `sha3`, `fp16`, `fp16fml`, `dotprod`, `i8mm`, …) | Enables it in the set, with its dependencies. clang 19 also takes `neon`, `fp-armv8`, `fullfp16`, `jsconv` and `complxnum` here. |
| Any other `no-x` | Raw `-x`. `no-neon` is raw `-neon`, which the touched `+neon` from the set overrides, so it changes nothing, as in clang. |
| A sub-architecture `v8.Na` / `v9.Na` | The level's features, as raw `+f` in clang 22. clang 19 enables the extension ones in the set. Then raw `+v8.Na`. |
| An LLVM name in `fp-armv8`, `neon`, `fullfp16`, `jsconv`, `complxnum`, `mte`, `rand` | Raw `+x`. |
| Anything else | Ignored (see the follow-ups). |

The result (`TargetAttrFeatures::features`) is the raw entries, then every
touched feature of the set with its final sign. Its `+` entries, in order,
are the attribute's own features for the `always_inline` check below.

This was verified against clang 19 and clang 22 for every probed string,
under `-march=` `armv8-a`, `armv8-a+nosimd`, `armv8.2-a+sha2+bf16` and
`armv8.6-a+nofp16`.

### Emit-time checks (clang `CodeGenFunction::checkTargetFeatures`)

These are codegen errors, so `-fsyntax-only` never reports them.

- **A NEON builtin call** whose required-features string does not hold
  for the caller's feature map is an error at the call's begin location:
  `cg_builtin_needs_feature`, "'%0' needs target feature %1". The message
  prints the whole string, for example `bf16,neon`. The call emits
  `poison`.
- **A direct call of an `always_inline` function** is checked when the
  callee or the caller has a `target("...")` attribute.
  - The callee's features are its attribute's `+` features in order
    (those still on), then the rest of its map.
  - When the callee has the attribute, the first feature the caller lacks
    is reported, as `cg_function_needs_feature`: "always_inline function
    '%1' requires target feature '%2', but would be inlined into function
    '%0' that is compiled without support for '%2'".
  - When only the caller has the attribute, each missing feature is
    reported separately.
  - Calls through a member access are not checked yet (see the
    follow-ups).

## bf16 lowering (`neon.rs`, clang `EmitAArch64BuiltinExpr`)

| Builtin | Intrinsic | Signature |
|---|---|---|
| `vbfdot_f32` | `llvm.aarch64.neon.bfdot.v2f32.v4bf16` | `<2 x float>(<2 x float>, <4 x bfloat>, <4 x bfloat>)` |
| `vbfdotq_f32` | `….bfdot.v4f32.v8bf16` | `<4 x float>(<4 x float>, <8 x bfloat>, <8 x bfloat>)` |
| `vbfmlalbq_f32` | `llvm.aarch64.neon.bfmlalb` | `<4 x float>(<4 x float>, <8 x bfloat>, <8 x bfloat>)` |
| `vbfmlaltq_f32` | `llvm.aarch64.neon.bfmlalt` | `<4 x float>(<4 x float>, <8 x bfloat>, <8 x bfloat>)` |
| `vbfmmlaq_f32` | `llvm.aarch64.neon.bfmmla` | `<4 x float>(<4 x float>, <8 x bfloat>, <8 x bfloat>)` |
| `vcvth_bf16_f32` | `llvm.aarch64.neon.bfcvt` | `bfloat(float)` |
| `__a64_vcvtq_low_bf16_f32` | `llvm.aarch64.neon.bfcvtn` | `<8 x bfloat>(<4 x float>)` |
| `vcvtq_high_bf16_f32` | `llvm.aarch64.neon.bfcvtn2` | `<8 x bfloat>(<8 x bfloat>, <4 x float>)` |

- **Operands.** All operands are emitted first, then each is bitcast to
  its parameter type. The trailing type-code immediate is dropped.
- **Results.** A bfdot result stays `<N x float>`. Every other result is
  bitcast to the builtin's declared type.
- **Intrinsic attributes.** The intrinsics are declared `nocallback
  nofree nosync nounwind willreturn memory(none)`
  (`kiln_llvm::intrinsics::target_nomem`).
- **Other NEON builtins.** The load/store, lane, splat and permute
  builtins are WP-628's table (spec/landed/codegen/WP-628.md). Any other
  NEON builtin that is emitted is the error "code generation for
  `<name>` is not supported yet". A
  declaration, or an uninstantiated or unused inline header function, is
  never emitted, so it never produces this error.
- **clang 22.** The `arm_neon.h` of clang 22 converts with `fptrunc`
  instead of `bfcvtn`, so the IR test pins clang 19.
