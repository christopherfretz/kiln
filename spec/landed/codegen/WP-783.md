# WP-783 — wide `template for` functions at `-O3`: IR-shape parity with clang

## Symptom

In one reflection-heavy TU of the reference workload, `-O3 -c` takes
457 s with kiln and 150 s with g++ 16.1. Nearly all of kiln's time is
spent in LLVM's `default<O3>` on a single function template. Its body
has about a dozen `template for` expansions ([stmt.expand], P1306),
`if constexpr` gates, and `for` loops over constexpr arrays, plus
string building that makes about 2,000 calls that may throw. The
function's pre-opt IR is large:

- 23,017 basic blocks;
- 8,206 invokes onto 2,000 cleanup landing pads;
- 5,968 allocas;
- 1,628 `llvm.memset` calls.

`opt` time breaks down as GVN 152 s, LoopFullUnroll 134 s and
IndVarSimplify 27 s. With `-ftrivial-auto-var-init=uninitialized` the
same TU took 498 s on a loaded host. The pass shares were unchanged, so
the erroneous-value pre-fill is not the cost.

## Finding: kiln's IR is clang's IR for the same source

No kiln IR-shape fault was found, so this WP changes no IR. Each
suspect was measured on std-only synthetic TUs. The bench entry below is
the tracked one. Each TU is either a `template for` over constexpr
indices, or its non-reflection twin with the same per-iteration body
expanded by a macro. A body builds an `ostringstream`, a
`std::set<std::string>` and string temporaries, calls two `noinline`
may-throw helpers, and loops over constexpr arrays.

Pre-opt IR was taken with `-O3 -S -emit-llvm -Xclang -disable-llvm-passes`.
The oracle is clang 19 under `-ftrivial-auto-var-init=zero`, which is the
fill P2795 gives kiln's C++26 default (§7r). These are the counts for one
100-iteration function in the twin:

| | blocks | invokes | landingpads | allocas | memsets | lifetime calls | `opt-19 default<O3>` |
|---|---:|---:|---:|---:|---:|---:|---:|
| kiln `-fclang-compat=19` | 4,224 | 1,415 | 1,004 | 2,395 | 546 | 4,672 | 3.75 s |
| clang 19 `=zero` | 4,215 | 1,412 | 1,001 | 2,426 | 546 | 4,771 | 3.56 s |

Both compilers rank the same three passes first: LoopFullUnroll about
36 %, LoopRotate about 18 % and SROA about 8.5 %. Every suspect matched
clang:

- **(a) Pre-fill.** kiln emits the same memsets as clang `=zero`. The
  real TU's run without any fill is no faster. §7r/§7y are unchanged.
- **(b) Cleanups.** Invokes and landing pads match clang to 0.3 %: the
  same sharing and one pad per cleanup scope.
- **(c) Loops.** A `template for` emits no loop. Each element's block
  follows the previous one, with `continue` jumping to the next element
  (`emit_expansion` in crates/kiln_codegen/src/stmt.rs). A range-`for`
  over a constexpr array has the same rotated-loop shape as clang's.
- **(d) Allocas and lifetimes.** Allocas and lifetime markers match
  within 2 %. The `template for` form adds one alloca and its lifetime
  markers per element, for the `constexpr` loop variable. The clang
  P2996 fork does the same.
- **Constexpr tables through `std::span`.** Lookups by id, by name and
  by group over a 400-entry constexpr table produce identical counts and
  `opt` times in kiln and clang 19. This holds whether the table is a
  namespace-scope `constexpr` array or `define_static_array` storage,
  which kiln emits as a `private unnamed_addr constant`.
- **`template for` itself.** Compared with the clang P2996 fork (clang 21,
  `-freflection -fexpansion-statements`) under `opt-22`, the shape is
  identical. `opt` takes 2.84 s on kiln's IR and 2.91 s on the fork's.
  On the forwarded synthetic cut to 60 items, `opt` takes 3.79 s on
  kiln's IR and 3.87 s on the fork's.

At full `-O3 -c` on the 100-iteration twin, kiln with its default
llvm-19 backend takes 6.15 s and clang 19 `=zero` takes 5.69 s (1.08x).
The pre-opt IR is the same, so the difference is outside what LLVM is
given: kiln's frontend takes 0.97 s to clang's 0.72 s, and kiln runs
LLVM as separate `opt`/`llc` processes. clang 22 is faster again because
of its newer LLVM, not a different IR shape: 4.61 s with `=zero`, against
kiln's 5.49 s in a separate run. At 300 iterations, kiln takes
46.3 s / 367 MB and clang 22 `=zero` 39.0 s / 364 MB.

Against g++ 16.1 on the `template for` form (both using libstdc++ 16):

| iterations | kiln | g++ 16.1 |
|---|---|---|
| 48 (bench) | 2.48 s / 100 MB | 3.88 s / 304 MB |
| 100 | 5.29 s / 144 MB | 9.06 s / 397 MB |
| 300 | 42.0 s / 347 MB | 54.8 s / 609 MB |

So kiln meets the 1.2x-of-g++ target on every std-only shape. A
300-item synthetic with table loops, forwarded with the report, also
reaches parity: 176 s with kiln against 172 s with g++.

**What is not reproduced.** The real TU's GVN share (about 47 % of
`opt`) does not appear in any std-only synthetic. There GVN stays at
5–8 %, and the loop passes lead. The remaining candidates have no clang
oracle:

- a lowering that only reflection reaches;
- LLVM's GVN (MemoryDependence) cost on that one function's mix of
  loads and calls.

Settling it needs the giant function's pre-opt IR, or a prefix-pipeline
`-time-passes -stats` run up to its first GVN. That is a follow-up.

## Proposal (follow-ups, not implemented here)

1. **Outline expansion elements.** WP-641 (spec/landed/codegen/WP-641.md)
   outlines runs of expression statements. A `template for` element is a
   compound statement, so a wide expansion is never outlined. Instead,
   when an optimized function's expansion statement has many elements
   whose bodies need EH cleanups, each element (or a chunk of elements)
   would be emitted as an internal `noinline` helper,
   `<parent>.expand.<n>`. As in WP-641, it would take the parent locals
   it names by pointer. Unlike WP-641, an element can `break`, `continue`
   or `return`, so the helper must return a status the parent switches
   on, and a returned value must go through the parent's return slot.
   Each helper would then be the size of one element, and the loop
   passes' superlinear cost would apply per element.
2. **Size-gated pipeline option.** An opt-in driver flag (not the
   default, which stays clang's `default<ON>`) could run `default<O2>`,
   or skip LoopFullUnroll, for a function over a block limit. This needs
   either a per-function pass gate (an `opt` plugin, which kiln's `opt`
   subprocess cannot load portably) or a split module, so it comes after
   item 1 and only if item 1 is not enough.

## Driver changes

- `-###` prints the `opt -passes=default<ON>` runs that `-v` shows,
  including the `-discard-value-names -S` run for `-S -emit-llvm`. It
  prints none at `-O0` and none under `-Xclang -disable-llvm-passes`
  (spec/driver.md "IR optimization").
- `-S -emit-llvm` writes the same module that the `-c` path hands to
  `llc`. Its lifetime intrinsics take the form the configured backend
  parses, so llvm-19's `opt` and `llc` read the text back. The old
  rewrite to LLVM 22's form is gone (spec/driver.md "IR optimization").
