# WP-1112 — P2719 type-aware allocation correctness tail

The three gaps WP-1088 left. The rules are in spec/sema.md §5.9 ("Type-aware allocation") and spec/oven.md ("Transient allocation"). The oracle is clang 22 (clang 22.1.8 sources: `SemaExprCXX.cpp`, `SemaDeclCXX.cpp`, `ExprConstant.cpp`). Every test is `//@ verify` with `requires: clang>=22`.

- **Ambiguous `operator new`** (`new_delete.rs`; clang `resolveAllocationOverloadInterior`, `OR_Ambiguous`).
  - `find_operator_new_template` returns `Err(notes)` on an ambiguous best candidate. The new-expression then gives `call to 'operator new' is ambiguous` (or `operator new[]`), with the ambiguous-candidate notes (`candidate function [with T = S]`).
  - The expression is invalid. There is no retry without the alignment and no untyped fallback. The coroutine frame lookup keeps its old behaviour (`.ok().flatten()`).
  - Test: `expr.new/type-aware-ambiguous.cpp` covers:
    - global and class-scope templates, a non-template, an array, and an instantiation;
    - a typed-over-untyped tie, which is not ambiguous;
    - a non-template over templates, which is not ambiguous either.
- **Malformed `std::type_identity`** (`overload/alloc.rs`, `alloc_decl.rs`; clang `LookupStdClassTemplate`, `tryBuildStdTypeIdentity`, `IsPotentiallyTypeAwareOperatorNewOrDelete`).
  - `lookup_std_type_identity` returns `StdTypeIdentity::{Absent, Malformed(decl), Template(tmpl)}`. A template is usable when it has exactly one required parameter, a type parameter that is not a pack.
  - `std_type_identity` reports a malformed one with the new `sema_malformed_std_class_template` at the declaration that lookup found. It does this on every use (`allow_duplicate`, as clang does not cache the lookup), and the expression falls back to the untyped functions.
  - An enumeration named `std::type_identity` now makes a declaration type-aware (`is_type_identity`).
  - `resolve_usual_dealloc`:
    - It skips typed candidates for an untyped want.
    - With a malformed lookup, it skips namespace-scope typed candidates without a diagnostic. clang makes them invalid, so lookup does not find them.
  - Completeness:
    - Building `std::type_identity<T>` no longer completes it.
    - A typed new-expression requires it complete at its start. An incomplete one makes the expression invalid.
    - `typed_usual_delete` requires the selected function's first parameter complete (clang `CheckDeleteOperator`).
  - Tests, all under `basic.stc.dynamic/`:
    - `type-aware-type-identity-{struct,enum,arity,nontype,pack}.cpp`;
    - `type-aware-type-identity-incomplete.cpp`;
    - `type-aware-type-identity-default.cpp`, a valid `template <class T, class U = int>`.
- **Direct call of a global typed operator in constant evaluation** (`kiln_oven/src/compile/new_delete.rs`; clang `HandleOperatorNewCall` / `HandleOperatorDeleteCall`).
  - `global_alloc_form` also accepts `is_type_aware_global_alloc`. `global_alloc_call` evaluates the `type_identity` argument for effect and takes the size or pointer from the next argument.
  - Outside `std::allocator<T>::allocate` / `deallocate`, the call gets the untyped-memory note (new) or `subexpression not valid` (delete), as clang does.
  - Test: `expr.const/type-aware-direct-call.cpp`.
- **Interface changes**:
  - New diagnostic `sema_malformed_std_class_template`.
  - `find_operator_new_template` returns `Result<Option<_>, Vec<Diag>>`.
  - New `Sema::lookup_std_type_identity` and `StdTypeIdentity`.
  - `std_type_identity` no longer requires completeness.
- **Divergences and follow-ups**:
  - clang marks the declarations of a malformed type-aware function invalid. kiln does not, because `is_type_aware_alloc_fn` uses invalid to mean "not type-aware". The visible behaviour matches.
  - Within `std::allocator<T>::allocate`, clang 22 reads a typed call's size from its first (`type_identity`) argument and allocates zero elements. kiln uses the size argument.
  - kiln has no malformed-`std::initializer_list` diagnostic, which uses the same clang lookup.
