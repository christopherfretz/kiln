# WP-668 — nlohmann/json through its own build: four frontend fixes

Building nlohmann/json v3.12.0's test suite with kiln++ (the project's
own CMake build and ctest; docs/status/oss/nlohmann-json.md) failed in 86
of 90 TUs on main f3751eadd. Four kiln bugs explained every failure; each
is fixed in its own commit with a conformance test and the sentence in
the spec named below. No runtime test failed under kiln once its TU
compiled.

## Fixed behaviours

- **Overload sets of members of a dependent class are type-dependent**
  ([temp.dep.expr]/3, [temp.dep.general]; clang `OverloadExpr`
  dependence). A `UnresolvedLookupExpr` naming any member of a class
  template's pattern (a decl with a dependent context) makes the call
  type-dependent even when the arguments are not, so SFINAE-selected
  static member templates (`to_char_type<C = CharType>(unsigned char)`
  overloads) are resolved per instantiation instead of being reported
  ambiguous at the definition. 85 of the 86 first-build failures.
  Spec: spec/sema-overload.md (after the WP-366 paragraph).
  Test: `tests/conformance/temp.dep.expr/member-template-overload-dependent-context.cpp`.
- **A braced string literal initializes a character array**
  ([dcl.init.string]/1, [dcl.init.list]/3.3). `char a[] = {"lit"}`, a
  member or element initializer `{"lit"}`, with or without a bound, for
  every character type, initializes the array from the literal
  (`Sema::braced_string_init`); a second element is `excess elements in
  char array initializer` (new id `sema_excess_initializers_in_char_array`,
  clang `err_excess_initializers_in_char_array_initializer`).
  Spec: spec/sema.md ("character arrays from string literals").
  Tests: `tests/conformance/dcl.init.string/braced-string-literal-run.cpp`,
  `braced-string-literal-excess.cpp`.
- **Out-of-line explicit specialization of a constructor, conversion
  function or `operator=` template** ([temp.expl.spec]/1,
  [temp.deduct.decl]). `template<> P::P(const J&) : P(1) {}` that
  matches no non-template constructor declares the specialization of
  the constructor template deduced from the declarator's type
  (`Sema::act_on_explicit_special_template_spec`, the counterpart of
  the WP-580 explicit-instantiation path); no match is clang's "no
  function template matches function template specialization 'P'" with
  the failed-deduction notes. It was "out-of-line definition of 'P' does
  not match any declaration".
  Spec: spec/sema-templates.md §2.5 "Explicit specialization".
  Tests: `tests/conformance/temp.expl.spec/special-member-template-spec-run.cpp`,
  `special-member-template-spec-no-match.cpp`.
- **`X<args>::m::name` in a template argument** ([temp.arg.general]/2,
  [basic.lookup.qual]). The parser's lookahead classifies a component
  after a member typedef `m` of a class template's pattern that names a
  class template specialization (`using m = Y<S>;`) in `Y`, as it does
  for `X<args>::name` (WP-130/WP-276), also through a typedef of
  `X<args>`; `is_same<A, oj::json_pointer::string_t>` takes a type-id.
  A qualifier in a dependent context keeps the member dependent
  (`Sema::member_typedef_class_template`).
  Spec: spec/parse.md (the `X<args>::name` lookahead bullets).
  Test: `tests/conformance/temp.arg.type/member-typedef-of-specialization-qualifier.cpp`.
