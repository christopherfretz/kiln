# WP-611 — a specialization's default access follows its own class-key

[class.access.base]/2, [class.access]/3, [temp.expl.spec],
[temp.spec.partial.general]. The rule is in `spec/sema-class.md` §2.1
item 2.

- An explicit specialization was created with the primary template's
  class-key (`get_class_spec` copies it into the new record) and kept it
  when its own class-head declared or defined it, so `template <class L>
  class traits {public: enum {Progress = 4};}; template <> struct
  traits<double> : traits<float> {};` inherited privately and
  `traits<double>::Progress` was "a private member of 'traits<float>'"
  ("constrained by implicitly private inheritance"); members before the
  first access-specifier of such a specialization were private too. A
  numeric-library traits header in real code has this shape.
  `act_on_explicit_class_spec` now re-keys a specialization not yet
  defined at each declaring class-head (`Sema::take_spec_class_key`), so
  the defining head's key sets the default base and member access; the
  reverse direction (`class` over a `struct` primary) makes both private,
  matching clang 19 and 22 diagnostic for diagnostic.
- A partial specialization already took its own key when first declared;
  a later defining head with the other key (`template <class T> class
  W<T *>; template <class T> struct W<T *> {...};`) now re-keys it as
  well, and its implicit instantiations take that key through the
  existing `start_instantiated_definition` path.
- `DeclArena::set_instantiated_tag` is renamed `set_definition_tag` (it
  now serves explicit and partial specializations as well).
- Tests: `temp.expl.spec/class-key-of-specialization-run.cpp`,
  `temp.expl.spec/class-key-of-specialization-errors.cpp` (strict-diags,
  the reverse direction),
  `temp.spec.partial.general/class-key-of-partial-specialization-run.cpp`.
