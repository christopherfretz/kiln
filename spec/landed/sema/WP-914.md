# WP-914 — rejects-valid and accepts-invalid batch

Four fixes found by the libc++ and clang test runs. It also closes WP-929, WP-1055 and WP-1057. Each fix is matched against clang 19 and clang 22.

- **Structured-binding `tuple_element` index** (WP-914; spec/sema.md §4.9, [dcl.struct.bind]/4, [temp.arg.nontype]/2).
  - Root cause: at `-fclang-compat=19` the index was an unconverted `size_t` value argument. So `template <unsigned I, class T> struct tuple_element` missed its explicit specialization for `0`.
  - Fix: `tuple_element_type` runs `check_template_args` on the `tuple_element` template at compat 19 too, so the index takes the parameter's type. Compat 22 (an integer literal written as an expression argument) is unchanged.
  - Tests in `dcl.struct.bind/`: `tuple-element-unsigned-index-19.cpp`, flipped from xfail; `tuple-element-unsigned-char-index{,-19}.cpp`, which pin each level's diagnostic for a mismatched specialization.
- **Enumerator named like an overload set** (WP-929; spec/sema.md §3 and §4.4, [basic.scope.scope]/4, [dcl.enum]/11).
  - Root cause: the redefinition check reported a clash with any earlier declaration of the name. clang only reports one when `LookupSingleName` + `getAsSingle` finds a single non-template entity.
  - Fix:
    - `lookup_current_scope_outside_enum` applies clang's single-entity rule.
    - Lookup skips an unscoped enumeration's own scope, so the enumerators are found together with the enclosing scope's functions.
    - A block-scope lookup that finds an enumerator also collects the functions of that name.
    - Ambiguity notes follow clang's order (`ambiguity_order`, `lexically_within`), and printed names skip an unscoped enumeration.
    - A member access `s.m` that finds functions plus an enumerator is `reference to 'm' is ambiguous`, where it used to be "not supported yet".
  - Tests in `basic.scope.scope/`: `enumerator-after-overload-set.cpp` is a run test of which declaration each use picks, at namespace, class, block and function-template scope. `enumerator-after-overload-set-ambiguous.cpp` is the strict invalid twin.
- **`__builtin_readcyclecounter`** (WP-1057; spec/sema.md §4.5 "Truthful feature tests", spec/codegen.md).
  - Root cause: `__has_builtin` answered 1 from clang's table, but the builtin was not declared, so a guarded use was "use of undeclared identifier".
  - Fix:
    - It is declared (`ULLi`) on every target, lowered to `llvm.readcyclecounter`, and not constant in the Oven.
    - The four `__builtin_` keywords the parser lacks answer 0 (`pp_cmd::UNPARSED_KEYWORD_BUILTINS`).
    - `kiln_driver/tests/builtin_lowering.rs` now also requires that no reported reserved-namespace builtin is undeclared, on both targets at compat 19 and 22.
  - Tests: `ext.gnu.builtins/readcyclecounter-{run,not-constant}.cpp` and `tests/codegen/builtin_readcyclecounter{,-19}.cpp`.
- **Library builtin rows** (WP-1055; spec/sema.md §5.4 "Library functions", §5.28 "Never constant").
  - Root cause: `bcmp` and `memcmp` were missing from `builtin::LIB`. So `bcmp(p, p, 1) + x` in gnu++20 was not reported as never constant.
  - Fix: added `memcmp`, plus the GNU-only rows `bcmp`, `bcopy`, `bzero`, `index`, `rindex`, `stpcpy`, `stpncpy`, `strdup` and `strndup` (`lib_gnu_only`). The audit against clang's `Builtins.td` found no other missing NoThrow/Const/Pure rows. The unmodelled attributes and lowerings are listed in spec/sema.md.
  - Tests in `dcl.constexpr/`: `never-constant-library-bcmp-gnu.cpp`; `never-constant-library-bcmp-cxx20.cpp`, where `bcmp` is an ordinary function.
