# WP-841 — correctness bundle 2 (WP-831, WP-840, WP-679, WP-693)

Four accepts-invalid, false-positive and missing-builtin gaps, each
matched against clang 19. WP-696 (flow-based `-Wuninitialized`) was
left to WP-862.

- **WP-831, a specialization of a class template inside its own
  definition** (spec/sema-templates.md §4.6 step 2):
  `typename basic<long>::type` or a field `basic<long> x;` inside
  `template<class S> struct basic` was looked up in the incomplete
  pattern. It is now clang's "implicit instantiation of template
  'basic<long>' within its own definition" (`DiagnoseUninstantiableTemplate`,
  no note), and the specialization is invalid. Silent once the pattern
  is invalid. The current instantiation, the injected-class-name and
  uses from member function bodies are unaffected. Tests:
  `temp.inst/specialization-within-own-definition-{member-typedef,field,valid}.cpp`
  (the first was an xfail).
- **WP-840, undefined but used entities** (spec/sema.md §5.2 "Undefined
  but used entities"; clang `checkUndefinedButUsed`): at the end of the
  TU, with no error, an odr-used function or variable that is still
  undefined is diagnosed at its first declaration, with "used here" at
  the first use. It is an error when it has external linkage but a type
  without linkage (a lambda, local or unnamed-namespace class in its
  signature: `template<class F> void g(F); g([]{});`), and
  `-Wundefined-internal` when it is not externally visible.
  `-Wundefined-inline` applies to an inline function. An inline
  variable is an error. A default argument's uses count only at a call
  that uses it; nothing in `std` is diagnosed (the evaluator supplies
  some of it). Tests:
  `basic.def.odr/undefined-but-used-{no-linkage-type,internal,valid,default-argument}.cpp`.
  Not done: clang's vtable-use marking (the virtual members of an
  unnamed-namespace class whose vtable is used), and qualified calls of
  an undefined pure virtual function.
- **WP-679, `-Wmissing-noreturn` on a lambda** (spec/sema.md §7.5.3):
  clang 22 `inferNoReturnAttr` infers `noreturn` silently for a lambda
  call operator below C++23 (`[](int, int) -> bool { throw 0; }` under
  `-std=c++20`). From C++23 on, it still warns. Tests:
  `dcl.attr.noreturn/missing-noreturn-lambda-{cxx20,cxx23}.cpp`.
- **WP-693, the printf/scanf family builtins** (spec/sema-templates.md
  builtin table, spec/codegen.md, spec/oven.md). These are added:
  `__builtin_printf`, `__builtin_vprintf`, `__builtin_vsprintf`
  (`NoThrow`, implicit `format(printf, F, A)`, checked by `-Wformat`),
  and `__builtin_scanf`, `__builtin_sscanf`, `__builtin_vscanf`,
  `__builtin_vsscanf` (not `NoThrow`, no format check). Each lowers to
  a call of the library function. clang 19 declares no
  `__builtin_fprintf`, `__builtin_vfprintf`, `__builtin_fscanf` or
  `__builtin_vfscanf`, so neither does kiln. Tests:
  `ext.gnu.builtins/printf-scanf-family-run.cpp`,
  `ext.gnu.builtins/format-printf-family.cpp`.
