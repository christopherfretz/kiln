# WP-826 — bound instantiation work after the first error

Boost.Math's reverse-mode autodiff compile-fail tests made kiln keep
instantiating long after the first error. Three of them hit the 3 GB
address-space limit, at 1.8 GB and 23 to 39 s CPU, while clang 19 stopped
at 0.44 to 0.6 GB and 4 to 5 s (docs/status/oss/boost_heavy.md,
Performance item 3). The error-recovery rules below now follow clang's
(spec/sema.md §1.2, spec/sema-templates.md §5.5 and §10.3).

- **Any fatal error stops instantiation.** clang's `InstantiatingTemplate`
  refuses every new instantiation once a fatal error has occurred,
  including the error limit's `fatal_too_many_errors`. Kiln used to latch
  `inst.fatal` only from its own instantiation-depth fatal. Now
  `Sema::instantiation_stopped()` (templ/stack.rs) also latches it from
  `diags.has_fatal()`, and every entry point checks it: pushing an
  instantiation frame, the end-of-TU loop, draining pending
  instantiations, and instantiating a function definition. Without this,
  kiln instantiated whole specialization graphs while printing nothing.
- **A failed `return` ends the body.** If a `return` operand does not
  convert, clang's `BuildReturnStmt` gives `StmtError`, so the function is
  invalid. Later calls to it are then "substitution failure" candidates
  rather than new instantiations. The Substituter now marks the body
  failed when a substituted `return` has an erroneous operand and the
  statement itself raised a new error. Errors from a nested instantiation
  don't count, and lambda bodies are excluded (`failed_return`,
  subst/stmts.rs).
- **A failed `then` branch ends the `if`.** clang's `TransformIfStmt`
  returns `StmtError` before transforming `else`, so kiln no longer
  instantiates the `else` branch after a failed `then` branch.
- **A condition over a failed local is still instantiated.** clang wraps a
  reference to an invalid local in a `RecoveryExpr`, so a condition over
  it is valid and both branches (and loop bodies, and a `for`
  increment) are instantiated and diagnosed. Kiln used to drop the whole
  statement and miss those errors. `recovering_expr` now builds an
  erroneous expression in that case, but only when the failure added no
  new error, an error is already pending, nothing is fatal, and this is
  not a pack probe. An `if constexpr` condition is never recovered.

## Numbers

Each TU was compiled by hand, one at a time, at host load ~23, from
`libs/math/test` of a `boost-1.90.0` checkout. Wall time is mostly
file-system waits, so user CPU and peak RSS are the figures. The command
lines are in boost_heavy.md, Performance item 3. Before is `f150c57c7`
under an RSS watchdog that killed it at ~3 GB. After is this WP.
Figures are user s / peak MB.

| TU (`…/test_reverse_mode_autodiff_<name>_compile_test_<ET>_multiprecision_float_types.cpp`) | before | after | clang-19 |
|---|---|---|---|
| factorial / rising_factorial / ET_ON | >= 87.4 / >= 3220, killed | 7.2 / 222 | 4.0 / 452 |
| beta / ibeta_inv / ET_ON | >= 34.1 / >= 2910, killed | 8.7 / 375 | 5.3 / 604 |
| beta / ibetac_inv / ET_ON | >= 34.0 / >= 2960, killed | 8.7 / 377 | 5.3 / 604 |
| bessel / cyl_neumann / ET_ON (sample) | 9.1 / 260 | 7.0 / 246 | 4.4 / 479 |

Under `ulimit -v 3000000` the same three "before" runs abort at 1.8 GB
after 28.7, 17.6 and 17.0 s. Six more TUs from the sample (tgamma, ibeta,
legendre_p, ellint_rj, zeta, and cyl_neumann above) take 7.0 to 7.9 s
and 230 to 250 MB, against clang's 4.3 to 4.8 s and 466 to 505 MB. On all
nine TUs kiln's first error matches clang's. Kiln also stops at the same
limit: 19 errors plus the fatal on the five TUs where clang reaches it,
and 3 to 10 errors against clang's 3 to 11 on the other four.

## Tests

- `temp.inst/fatal-error-stops-pending-instantiation.cpp`, kiln-only, with
  an `inst-report` golden. After the error-limit fatal, a pending
  instantiation stays uninstantiated.
- `temp.inst/error-limit-stops-instantiation.cpp`. With
  `-ferror-limit=2`, kiln stops at the limit with clang's exact errors and
  note.
- `temp.inst/condition-over-failed-local.cpp`. Checks `if`, `else`,
  `while`, `for`, a `for` increment, `switch`, a failed `then` statement,
  a failed `then` declaration and a failed `then` return. It uses
  `-ferror-limit=0`, and its 13 errors are clang's, in clang's order.

## Not done

- clang recovers a typedef whose type fails substitution as `int`, and
  then diagnoses uses of it, e.g. `converter_lexical.hpp:452:66` in seven
  of the TUs. Kiln drops the declaration silently.
- A local whose initializer is a failed overloaded call stays valid in
  clang, because the initializer is a `RecoveryExpr`. Kiln treats that
  local as failed, so `n == 1 ? T() : 0` over it is diagnosed by clang
  and not by kiln.
- Wall time on these TUs is dominated by header search (WP-820).
