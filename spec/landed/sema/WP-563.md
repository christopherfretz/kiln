# WP-563 — Conversion-function template inside an enclosing template instantiation is deduced from its own parameters

Extends spec/sema-templates.md §5.4 ("Implicit nodes are stripped") and
spec/sema-overload.md (conversion function templates). GCC 16.1 and
clang 19/22 accept every accepted case below.

## The implicit conversion is redone, not re-looked-up ([temp.deduct.conv]/1, [temp.inst]/1)

- Inside an instantiation of a function template, a member function of a
  class template or a lambda in one, `handle h = g;` with `g` a local of
  class type whose `template <class U> operator U()` was chosen at the
  definition reported `no member named 'operator E' in 'getter'` (with
  `E` the enclosing instantiation's first argument). The definition's
  initializer is instantiation-dependent (it names a local), so it was
  rebuilt; its `ImplicitCastExpr <UserDefinedConversion>` was stripped,
  but the `CXXMemberCallExpr` under it was rebuilt by name, and the
  specialization's name is the pattern's `operator U`. `U` (depth 0,
  index 0 of the non-template class; depth 1 of a class template member)
  was substituted with the enclosing instantiation's argument of the
  same position.
- The substituter now strips such a cast down to the call's object
  argument (`Substituter::udc_object`, used by `expr_node` and
  `peel_initializer`; clang `CastExpr::getSubExprAsWritten`), and the
  enclosing action performs the conversion again from the substituted
  object, deducing the member template from the target type. Covers
  copy-init, direct-init, `static_cast`, functional casts, `return`,
  contextual conversion to `bool`, lambdas (also generic ones), member
  templates of class templates, and the constrained `const &` / `&&`
  overload pair (`enable_if_t<is_base_of_v<…>>`).
- A conversion whose deduction genuinely fails (unsatisfied constraint)
  is still "no viable conversion", at the definition when non-dependent
  and at the instantiation when dependent.

Tests: tests/conformance/temp.deduct.conv/conversion-template-in-enclosing-template-run.cpp,
tests/conformance/temp.deduct.conv/conversion-template-in-enclosing-template-errors.cpp.

Not covered (pre-existing, also outside templates): naming a conversion
function template specialization explicitly by its conversion-function-id
(`g.operator handle()`, [temp.mem]) is "no member named".
