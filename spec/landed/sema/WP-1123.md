# WP-1123 — constexpr declaration validity tails

Four accepts-invalid gaps found by WP-455's clang probes. The contract is spec/sema.md §5.20 ("Literal return and parameter types", "`constexpr` destructor before C++20", "C++11 deduced return type") and §5.28 "Never constant". Every behaviour below matches clang++-19 and clang++-22, which agree.

- **Literal return and parameter types before C++23** ([dcl.constexpr]/3, removed by P2448R2).
  - Root cause: kiln had no `CheckConstexprReturnType` / `CheckConstexprParameterTypes`. It accepted a non-literal parameter, and a non-literal return type fell through to the never-constant check. In C++11 `constexpr void f() {}` got "no return statement" instead of "return type 'void' is not a literal type".
  - Fix: `constexpr_body.rs` `check_constexpr_signature`, run by `check_constexpr_definition` between the virtual-base rule and the body rules, in clang's order. The new diag ids are `sema_constexpr_non_literal_return` and `sema_constexpr_non_literal_param`. On failure the function is made invalid.
  - Not checked: C++23 and later, dependent or undeduced types, incomplete classes, and instantiations (clang checks only the written definition).
  - `class/members.rs` `with_non_literal_notes`: before C++20 the note names a user-provided destructor (`note_non_literal_user_provided_dtor`).
  - An implicitly constexpr lambda with a non-literal return or parameter type is silently not constexpr.
  - The xfail `dcl.constexpr/non-literal-return-param-cxx20.cpp` is flipped.
- **`constexpr` destructor before C++20.**
  - Fix: `decl.rs` `act_on_special_member_declarator` emits `sema_constexpr_dtor`, "destructor cannot be declared constexpr", at the specifier.
  - The specifier is kept, as in clang, so a C++11 definition also gets the `void` return-type error.
- **C++11 `auto` function without a trailing return type.**
  - Fix: `decl.rs` `type_for_declarator_at`, through `cxx11_deduced_return`.
  - The error is `sema_auto_missing_trailing_return` for `auto` and `sema_deduced_return_type_cxx14` for `decltype(auto)`.
  - It applies only to the named declarator's function chunk next to the name, so a lambda's implicit `auto` is exempt. The return type recovers as `int`.
- **Never-constant check of lambdas and other walked functions.**
  - Root cause: lambdas did get the check. But any function that is not a parameterless free or static function is walked (`nc_stmt`), not evaluated as a call, and the walk did two things wrong:
    - it stopped at every static local;
    - it never failed at the end of the body.
  - That missed `[]() constexpr -> int {}` (C++23, `-Winvalid-constexpr`), `[]() constexpr { static int i = 0; return i; }` (C++20) and the same in non-static members.
  - Fix in `never_constant.rs`. The walk now fails on:
    - a static or `thread_local` local not usable in constant expressions (`nc_static_local`);
    - reaching the `}` of a non-void function (`nc_reaches_end_fails`).
  - Conservative guards keep it from ever reporting what clang accepts:
    - Both failures are skipped once a statement's unknown value involved a call (`nc_note_unknown`). clang continues past an unknown-argument call but stops quietly after a callee's failure, and the walk cannot tell the two apart.
    - A block that defines an unknown or non-trivially-destructible local stops the walk at its end.
    - `[[assume]]` stops the walk.
    - A block-scope `extern` declaration is skipped.
  - The Oven (`compile.rs`):
    - `is_local_var` no longer treats a `thread_local` local as automatic;
    - the static-definition trap covers `thread_local`;
    - the trap spares a `const` integral or enumeration static.
