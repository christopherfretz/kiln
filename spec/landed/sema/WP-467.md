# WP-467 — WP-454 follow-ups: structured bindings, constexpr references

- **`get<i>` index type.** A tuple-like binding's `get<i>` call
  (`decompose_tuple_binding`, [dcl.struct.bind]/4) writes `i` as a
  `std::size_t` integer literal expression argument, as clang's
  `getTrivialIntegralTemplateArgument` does, instead of a pre-converted
  `size_t` value argument (`size_t_arg`, which `check_template_arg`
  accepts unconverted). The literal is a converted constant expression
  of the parameter's type ([temp.arg.nontype]/2), so `template <int I>
  int& get(P&)` is `get<0>` with an `int` argument and mangles
  `_ZN1N3getILi0EEERiRNS_1PE` on both targets (it was `ILm0E`), a member
  `template <unsigned char I>` `ILh0E`. `tuple_element<i, E>` keeps its
  §4.9 form. Test: `tests/codegen/struct_bind_get_mangling.cpp` (both
  oracles).
- **P2686R5 constexpr-referenceable automatic objects** (C++26,
  [expr.const.init]/2,4, [expr.const]/8-9). A constexpr reference,
  pointer or structured binding in a function may designate an automatic
  object of the same function (not from a `static` variable, a lambda
  body or after the function returns): the Oven freezes the pointer as
  `PtrBase::Decl` when `Oven::referenceable_from_object` holds; sema's
  `representable_here` limits usability to that function, so a lambda
  captures such a variable; codegen drops folds whose value designates an
  automatic object (`kiln_oven::automatic_referent`). No oracle (clang 22
  and GCC 16 reject it): tests are `skip(clang)`; the C++23 rule stays in
  `expr.const/pointer-to-automatic-errors.cpp` and
  `dcl.constexpr/ptr-to-local.cpp` (now `std: c++23`), and the AST tests
  `dcl.struct.bind/{array,bitfield,tuple-adl-get}.cpp` are pinned to
  C++23 (at C++26 their reference `e` is constant-initialized). Spec:
  spec/sema.md §4.9, spec/oven.md "Freezing", spec/codegen.md `fold.rs`.
