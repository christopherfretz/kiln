# WP-962 — accepts-invalid fixes, part 1

These are the never-constant false positives, the parameter-tag panic and the empty `initializer_list` stack overflow found by WP-912's clang negative-test run. It closes WP-945 and the crash parts of WP-946/947. Each fix is matched against clang 19.

- **Never-constant false positives** (spec/sema.md §5.28 `-Winteger-overflow`, "Never constant"; `never_constant.rs`).
  - Root cause: the walk evaluated a direct call's callee operand on its own.
    - For a builtin, that operand is the `BuiltinFnToPtr` decay, and the Oven answered "kiln: constant evaluation of ImplicitCastExpr is not supported yet".
    - For a consteval operator template it gave "pointer to a consteval declaration is not a constant expression".
    - Either note was taken as proof that the function never produces a constant.
  - Fix, in three parts:
    - The callee of a direct call (`nc_direct_callee`) is never evaluated as a value.
    - A note that starts with `kiln:` (an Oven limitation) is never reportable.
    - A call of a builtin is opaque unless its row in `templ/builtins/table.rs` is `Oven::No`. The walk only checks such a call's arguments, and an unknown-free evaluation that fails is decomposed when it calls an opaque builtin.
  - Audit against clang 19's `__has_constexpr_builtin`:
    - Every `Oven::No` row is non-constexpr in clang, so those calls are still reported (`strstr`, `alloca`, `pow`).
    - The only `Oven::Yes` rows that clang 19 rejects are clang 22 additions and kiln extensions.
    - Builtins that are missing from the table are opaque. That is conservative: `__builtin_floor(2.5) + x` is not reported.
  - Tests in `dcl.constexpr/`:
    - `potential-constant-builtin-{fabs,strcmp}.cpp` and `potential-constant-consteval-operator-template.cpp`, flipped from xfail;
    - `potential-constant-builtins-spread.cpp`;
    - `potential-constant-builtin-bswap-cxx17.cpp`, the endian-helper pattern under `-Winvalid-constexpr`;
    - `potential-constant-unsupported-node-cxx17.cpp`;
    - `potential-constant-builtin-not-constexpr.cpp`, a true positive.
- **Parameter-tag panic** (spec/sema.md §4.4, [dcl.fct]/17).
  - Root cause: `act_on_tag` declared a tag defined in an out-of-line member's parameter clause in the current context. That context was the complete class, whose member list is frozen (`append_member` panics).
  - Fix:
    - Such a tag is declared in the nearest enclosing context that is not a complete class (`tag_home`).
    - The parser reports clang's "'S' cannot be defined in a parameter type" ("(null)" for an unnamed tag) for a function, lambda or requires-expression parameter.
    - The parameter is invalid, so a member or constructor definition gets no follow-on mismatch error.
  - Tests in `dcl.fct/`: `type-defined-in-{member-parameter-crash,parameter}.cpp`, flipped from xfail, and `type-defined-in-parameter-kinds.cpp`.
- **Empty `initializer_list` stack overflow** (spec/sema.md §6, [dcl.init.list]/3.6, CWG1070).
  - Root cause: `std::initializer_list<E>` from `{}` went through [over.match.list] when the specialization had no default constructor. Its own implicit copy constructor counted as an initializer-list constructor (its parameter is a reference to `initializer_list<E>`). Selecting it list-initialized the reference's temporary from the same `{}`, without bound.
  - Fix:
    - An empty list for a specialization with no default constructor builds the `CXXStdInitializerListExpr` over a `const E[0]` backing array. An incomplete `E` is clang's "initialization of incomplete type".
    - `init_list_ctor_init` never handles an `initializer_list` specialization.
    - A visited guard (`Sema::list_ctor_active`: the class and the `{` of the list) stops any re-entry of the same selection. The re-entered list then takes the ordinary constructor path, which diagnoses.
  - Tests in `dcl.init.list/`: `empty-initializer-list-no-default-ctor.cpp`, flipped from xfail, and `empty-initializer-list-no-default-ctor-run.cpp`, where `size()` is 0 at run time and in a constant expression.
