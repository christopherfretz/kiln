# WP-1078 — accepts-invalid: implicit overriders, nested exception specs, `enum F;`

Closes the three gaps WP-957 deferred from docs/status/accepts-invalid.md
item 12 (WP-912's clang negative-test run). It covers WP-1078, WP-1079
and WP-1080. Every case is matched against clang 19 and clang 22.

## Items

1. **Implicit overriders: `final` and the return type (WP-1078).** An
   implicitly declared destructor or copy or move assignment operator that
   overrides a base virtual function is checked as a declared overrider
   is ([class.virtual]/4, /8). It may not override a `final` function, and
   its return type (`D&`) must match the overridden one or be covariant
   with it. Both errors are reported at the class name, once per
   overridden function, and the explicit overrider's duplicate (two bases)
   is no longer folded. The checks run in a new `SynthKind::Declaring`
   synthesis context, so the first error of each implicit declaration
   carries clang's `while declaring the implicit copy assignment operator
   for 'D'` (`note_in_declaration_of_implicit_special_member`). In a class
   template specialization it comes before `in instantiation of template
   class ... requested here`. spec/sema.md "Overriders". Tests:
   `class.virtual/implicit-overrider{,-ok}.cpp`.
2. **Nested function types in overriders (WP-1079).** Clang's
   `CheckParamExceptionSpec` (C++14 [except.spec]/5, kept in every mode)
   runs once the overrider's own specification passes the subset check.
   Function types among the return and parameter types must have
   equivalent specifications: `exception specifications of argument types
   differ` / `... of return types differ`, at the overrider, with no note.
   Two fixes to the shared helper (also used by [conv.fctptr] conversions):
   - no specification and `noexcept(false)` are not equivalent;
   - each target (base) parameter type is compared with the source's
     (overrider's) FIRST parameter type. This is clang 19 and 22's
     behaviour: their loop indexes the source with a constant.

   From C++17 only the return-type cases remain (a differing parameter
   type overrides nothing), alongside clang 22's `different return type`.
   spec/sema.md "Overriders". Tests:
   `except.spec/override-nested-exception-spec-{cxx14,cxx17,ok}.cpp`.
3. **`enum F;` without an enum-base (WP-1080).** [dcl.enum]/2 and
   [dcl.type.elab]/3. An unscoped opaque declaration, or a first-use
   elaborated `enum K`, gets the error `ISO C++ forbids forward references
   to 'enum' types` at the name. This does not apply when the name is an
   enumeration already defined or already declared with a fixed
   underlying type. Clang reports it as an error in C++ mode. Only
   `-fms-compatibility` makes it a warning, and kiln has no such flag.
   spec/sema.md "Elaborated-type-specifier checks". Tests:
   `dcl.enum/forward-ref-enum{,-ok}.cpp`.

## Deferred (not in scope)

- `exception specifications are not allowed beyond a single level of
  indirection` (clang `CheckDistantExceptionSpec`) is not diagnosed, e.g.
  for a `void (**)() throw()` parameter. Kiln instead reports the nested
  mismatch on such parameters.
- C++17: an overrider parameter `void (*)() noexcept(false)` against a
  base's `void (*)()` is not diagnosed (clang 19 and 22: `exception
  specifications of argument types differ`). Before C++17 it is.
- `-Wfinal-dtor-non-final-class` and the pedantic `-Wgnu-redeclared-enum`
  warnings.
- The calling-convention check (`check_override_cc`) does not run for
  implicit overriders.
