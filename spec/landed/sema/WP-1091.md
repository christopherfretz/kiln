# WP-1091 — accepts-invalid tail of WP-1040: shadowing and declaration context

WP-1040's triage of clang's negative tests left four accepts-invalid
items. kiln now rejects each one with clang's diagnostic and location
(clang 19 and 22 agree unless noted). The rules are in spec/sema.md
(§4.1.1, §4.3.1, the template-declaration-scope and template parameter
shadowing bullets), spec/parse.md §2.4 and spec/abi.md §8.6.

1. **Elaborated reference shadowing a template parameter** ([temp.local]/6,
   clang `CXX/temp/temp.res/temp.local/p6.cpp:63`). An unqualified
   `struct T *p` whose ordinary lookup finds a template type or template
   template parameter is "declaration of 'T' shadows template parameter"
   at the name, with "template parameter is declared here"
   (`Sema::diagnose_tag_ref_template_param`, `kiln_sema/src/decl.rs`). The
   reference then names the tag `T` already declared in the enclosing
   namespace, or declares it there, so a second reference is not reported
   again and is not ambiguous. Tests:
   `temp.local/p6-elaborated-ref-shadows-template-param{,-ok}.cpp`.
2. **Lambda capture shadowing a template parameter**
   ([expr.prim.lambda.capture]/5, clang
   `CXX/expr/expr.prim/expr.prim.lambda/expr.prim.lambda.capture/p5.cpp:7`).
   A capture (simple, by-reference, init- or pack) named like a template
   parameter of the lambda's own explicit or invented head is the same
   error at the capture, with the note at the parameter
   (`check_capture_shadows_template_param`, `kiln_sema/src/lambda/capture.rs`).
   It runs from `act_on_lambda_declarator` once the head is complete. An
   enclosing template's parameters do not count. Tests:
   `expr.prim.lambda.capture/capture-shadows-template-param{,-ok}.cpp`.
3. **`__restrict` and nullability as method qualifiers** ([dcl.fct]/6,
   clang `SemaCXX/cxx2b-deducing-this.cpp:27-28`). kiln could not parse
   either keyword after a parameter list.
   - Parser: `parse_function_qualifiers` takes `__restrict`/`__restrict__`
     as a cv-qualifier (its location in `Declarator::fn_qual_locs[3]`; a
     repeat is `-Wduplicate-decl-specifier`). It takes a nullability
     keyword as `Declarator::fn_nullability`; the keyword is not part of
     the type.
   - Diagnostics: the explicit-object, static-member and non-member checks
     spell the qualifier `__restrict` ("explicit object member function
     cannot have '__restrict' qualifier", at the first qualifier). A lone
     nullability keyword gives an empty spelling ("... cannot have ''
     qualifier") at the start of the decl-specifiers
     (`diag_nullability_only_fn_quals`).
   - Valid uses: `this` is `T * __restrict` (`this_pointer_type`), and the
     object binding keeps only the cv-qualifiers. Restrict is not a basis
     for overloading (`void f() __restrict; void f();` is "class member
     cannot be redeclared"). The mangled method name leaves out `r`
     (`_ZN1T2okEv`), while a pointer-to-member type keeps it (`M1TrFivE`).
   - Restrict on a placeholder is now an error, as in clang: `auto
     __restrict p = &i;`, `void g(auto __restrict x)` and `this auto
     __restrict self` give "restrict requires a pointer or reference
     ('auto' is invalid)", or "('C auto' is invalid)" for a constrained
     placeholder (`restrict_ok`, `reject_placeholder_restrict`).
   - Tests: `dcl.fct/explicit-object-restrict-nullability-qualifier.cpp`,
     `dcl.fct/fn-restrict-nullability-qualifier-context.cpp`,
     `class.this/restrict-method-qualifier-run.cpp` and
     `tests/mangle/restrict_method.cpp`.
4. **Block-scope function template definitions** ([dcl.fct.def.general]/2).
   clang 22's `ParseSingleDeclarationAfterTemplate` reports "function
   definition is not allowed here" at the `{`, before its template-scope
   check. `Parser::block_scope_template` (`kiln_parse/src/stmt.rs`) now
   does the same under `-fclang-compat=22`, using a token scan
   (`block_template_function_body`), and skips the body. Other block-scope
   template-declarations keep WP-1063's "templates can only be declared in
   namespace or class scope". Under clang 19 both give "expected
   expression". Non-template block-scope definitions were already
   rejected. Tests:
   `dcl.fct.def.general/block-scope-function-template-definition{,-19,-ok}.cpp`.

Not done (follow-ups):
- `noalias` on a restrict `this` and on any `__restrict` pointer parameter
  in codegen. kiln emits none; clang does.
- "ISO C++ forbids forward references to 'enum' types" is missing, so the
  enum line of temp.local/p6.cpp still differs.
- clang 22 places the '' location at a leading attribute
  (`[[nodiscard]] static int f() _Nonnull;`); kiln, like clang 19, places
  it at the decl-specifiers.
- Error recovery after a skipped block-scope template differs from clang
  in a few cases: an `= delete` body, a missing `;` after a declaration,
  and a lambda in a variable template's initializer.
- An out-of-line definition whose `__restrict` differs from the
  declaration gives kiln's "out-of-line definition ... does not match"
  where clang says "conflicting types".
- GNU `__auto_type` is not implemented.
