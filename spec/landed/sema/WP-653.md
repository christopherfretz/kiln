# WP-653 — The NEON builtin table as plain data, and packed relative relocations (start-up RSS)

Extends spec/landed/sema/WP-558.md "Table" and "Ids and lookup" (the
NEON table and its lookups) the way spec/landed/sema/WP-652.md did for
the x86 table, and spec/driver.md "Driver modes" (how `kiln` is linked).
The measurements and the before/after tables are in
docs/status/perf-reflection.md "WP-653: NEON table and start-up
relocations". Nothing observable changes: the rows, their ids,
prototypes, attributes and features are those WP-558 generated, and every
lookup answers as before.

## The cost it removes

kiln++ is a position-independent executable. Before this package the
NEON table was a `const` slice of rows holding three `&'static str`
fields (name, prototype, features):
- each crate or codegen unit that inlined an accessor got its own copy,
  four in the release binary (1,081 rows of 56 bytes each in
  `.data.rel.ro`);
- each copy carried 3,243 `R_AARCH64_RELATIVE` relocations (72 bytes of
  `.rela.dyn` a row), which the loader reads and applies at every start,
  dirtying every page of the copy.

That was about 0.9 MB of binary read or dirtied before `main` on every
compile.

## Layout

`scripts/gen-neon-builtins.py` writes `crates/kiln_ast/src/neon_builtins.rs`
as two `static`s, so the binary holds one copy:
- `STRS: &str`: the names in row order, then each distinct prototype and
  features string once (ASCII; 30,561 bytes);
- `NEON: [Packed; 1081]`: per row, `(offset, length)` of the name,
  prototype and features in `STRS`, as `u32`/`u8` pairs (16 bytes a row,
  no pointers). Each row carries its name as a comment.

The rows are `.rodata`: no relocation (one for `STRS` itself), nothing
dirtied, and a page is read only when a lookup touches it. The
generator's `--reemit` rewrites the file from its own rows (this layout
or the pre-WP-653 one) without a clang build directory; it was used for
this change, and parsing both layouts gives the same 1,081 rows.

## Lookups (`kiln_ast::decl::builtin::neon`)

- `by_name` is a binary search over the packed rows, comparing names
  sliced from `STRS`; `is_neon` is a range check on the id.
- `row(id) -> Option<Row>` decodes the row and returns it **by value**
  (it returned `Option<&'static Row>`). `Row` is unchanged: `info`
  (`&'static str` name and prototype, attributes `NOTHROW`) and
  `features`.
- `all()` is replaced by `rows()` (an iterator of decoded rows) and
  `len()`.
- `builtin::info(id)` already returned `Option<Info>` by value
  (WP-652); NEON rows are now decoded on access as x86 rows are.

## The generic builtin lists

The fifteen `Info` lists in `kiln_ast::decl::builtin` (`ALL`, `CORO`,
`LIB`, `INT_MEM`, `LIBM`, `ATOMIC`, `SYNC`, `CHECKED`, `EXTRA`, `F128`,
`FLOATN`, `F16_INTR`, `F16_LIBM`, `C_MATH_INTR`, `C_MATH_LIB`) are
`pub static` instead of `pub const`. Each was measured at one copy in the
release binary already, so the binary does not change; `static`
guarantees it stays one copy as callers are added in other crates.

## Linking

**Reverted by WP-662**: the binary failed to start on a glibc older than
2.36 (`version 'GLIBC_ABI_DT_RELR' not found`), and a run-time platform
requirement is not worth 0.2–0.5 MB of start-up RSS. The measurement
below stands as the record of what the flag would give. On a Linux target `kiln_driver`'s build script passes
`-Wl,-z,pack-relative-relocs` when linking the `kiln` binary (every
profile; GNU ld 2.38+, lld 15+, rust-lld; the binary then needs glibc
2.36+, `GLIBC_ABI_DT_RELR`). The remaining relative relocations become a
`.relr.dyn` bitmap (8,832 bytes) instead of 24 bytes each in `.rela.dyn`
(685,776 bytes before, 312 after), so the loader reads about 9 KB of
relocations at start-up instead of 670 KB. The patched `.data.rel.ro`
pages are still written. It is a
link argument for the `kiln` binary only, so it does not change any
dependency's build or the test binaries.

## Tests

`crates/kiln_ast/tests/neon_builtin_table.rs`: every row decodes, its id
is `BASE` plus its index, `by_name` and `builtin::by_name` find it,
`builtin::info` and `required_features` agree with it, the names are
sorted and carry the `__builtin_neon_` prefix; the table's rows hash
(FNV-1a over name, prototype and features) to the pre-WP-653 table's;
fourteen sample rows from the old literal table carry their prototype,
attributes and features, and their features gate as before
(`features_hold`, `first_missing`); ids outside the table are not NEON
builtins.
