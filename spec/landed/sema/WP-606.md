# WP-606 — Accept (and ignore) clang's thread-safety-analysis attribute family

[dcl.attr.grammar]/6, [dcl.attr.unknown]. The rule is in `spec/sema.md`
§4.5, "Known and ignored, no diagnostic: the thread-safety family".

- kiln defines `__clang__`, so thread-annotation headers expand their
  macros to `__attribute__((guarded_by(mu)))`, `lockable`,
  `exclusive_locks_required(...)` and the rest; each was `unknown
  attribute 'x' ignored` [-Wunknown-attributes], fatal under a library's
  `-Werror`.
- `decl_attrs.rs` `THREAD_SAFETY_ATTRS` lists the 34 names with whether
  clang spells each `Clang<"x">` (GNU and `[[clang::x]]`) or only
  `GNU<"x">`, and the first clang release that knows it
  (`reentrant_capability`: 22). `attribute_node` checks it before any
  other handling and returns `None` silently for a match; `[[gnu::x]]`,
  unscoped `[[x]]` and `[[clang::x]]` of a GNU-only name stay unknown,
  as in clang 19 and 22.
- The parser already skipped the arguments of these attributes as
  balanced tokens (they are not in `takes_expr_args`), so arguments
  naming later members, `this`, `!mu`, `*f()` are accepted unevaluated.
  `__has_attribute` / `__has_cpp_attribute` already answered from the
  generated clang table.
- Tests (`tests/conformance/dcl.attr.grammar/`):
  `thread-safety-attributes-gnu.cpp` (every name, every position, `-Werror
  -Wunknown-attributes`), `thread-safety-attributes-clang.cpp` (the
  `Clang<"x">` names as `[[clang::x]]`), `thread-safety-has-attribute.cpp`,
  `thread-safety-attributes-run.cpp`, `thread-safety-attributes-unknown.cpp`
  (near misses still warn), `thread-safety-reentrant-capability-19.cpp`
  (`clang<22`: unknown at 19).
- Not yet: clang's argument lookup (an undeclared name is an error in
  clang), subject warnings, argument-count errors and `cannot be applied
  to types` for `[[clang::x]]` after a function declarator.
