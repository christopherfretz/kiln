# WP-558 — arm_neon.h bf16 builtins

Extends spec/sema.md §5.4 (builtin functions) and §4.5 (vector types),
spec/pp.md (`__has_builtin`) and spec/abi.md (mangling). The codegen
half (target features, emit-time checks, bf16 lowering) is
spec/landed/codegen/WP-558.md.

## Target builtins

Before WP-558, sema declared no `__builtin_neon_*` name: the 664 NEON rows
of `crates/kiln_pp/src/features_table.rs` only answered `__has_builtin`.
The macros of `<arm_neon.h>` (`vget_lane_*`, `splat_lane_*`, …) name
builtins only when expanded, so the header first failed at line 225, the
first `static __inline__` function body naming one (`vbfdotq_f32`).

- **Table.** `crates/kiln_ast/src/neon_builtins.rs` is generated by
  `scripts/gen-neon-builtins.py` (do not edit it). It holds every
  `__builtin_neon_*` name `resource/include/arm_neon.h` and `arm_fp16.h`
  reference, 1081 rows sorted by name. Each row carries the prototype in
  `Builtins.td` notation, the attribute string (always `n`, nothrow) and
  clang's `TARGET_BUILTIN` required-features string. The prototypes come
  from a clang >= 21 build's `arm_neon.inc` / `arm_fp16.inc`. The few
  names clang 21 dropped (`__a64_vcvtq_low_bf16_f32`, …) are listed in
  the script with clang 19's AST types. With `--check`, the script
  confirms each row's `__has_builtin` answer against `clang++-19 -E`.
- **Ids and lookup** (`kiln_ast::decl::builtin::neon`). A row's id is
  `neon::BASE` plus its index, so a name lookup is a binary search and an
  id lookup is an index. `by_name_at` falls back to it, so these names go
  through clang's `LazilyCreateBuiltin` path (spec/sema.md §5.4) like
  every other builtin: they are declared on the first unqualified lookup
  that finds nothing.
- **Prototypes.** The decoder (`kiln_sema/src/builtins.rs`) adds the NEON
  codes to the existing ones: `S` signed (`Sc` is `signed char`), `W`
  `int64_t` (`long`), `V<N>` a GNU vector of `N` elements, `h` `__fp16`,
  `y` `__bf16`, and `LLL` `__int128`. The header passes every vector
  through a cast to `int8x16_t` and similar types, and the
  `V16Sc`-style parameters accept that, as in clang. The trailing `i`
  is the type-code immediate (clang `NeonTypeFlags`).
- **AArch64 only.** On any other triple the names are not builtins:
  `lazily_create_builtin` returns nothing, and `__has_builtin` answers 0.
- **Declared unconditionally, checked at the call.** The required
  features are never checked in sema. A call that `-fsyntax-only` accepts
  is diagnosed only when codegen emits it (spec/landed/codegen/WP-558.md
  "Target features"), as in clang.
- **`__has_builtin`** (spec/pp.md). `kiln_pp::TargetBuiltins`, installed
  with `ClangFeatures::with_target_builtins`, answers the names starting
  with `__builtin_neon_` from the enabled features that the driver
  resolves from `-march`/`-mcpu`/`+ext`. The answer is clang's
  `evaluateRequiredTargetFeatures`: `,` means all of, `|` means any of.
  `bf16,neon` is 0 under the default `armv8-a` and 1 under
  `-march=armv8.6-a` or `+bf16`. Other names keep the table's answer.

## `neon_vector_type` / `neon_polyvector_type` ([dcl.attr], clang `HandleNeonVectorTypeAttr`)

The header's vector typedefs use these attributes (kiln_sema
`vector.rs`):

- `N` is an integral constant element count.
- The element must be a type that clang's `isPermittedNeonBaseType`
  accepts, seen through typedefs. Plain `char` is not accepted. A
  dependent element is not accepted either.
- The vector must be 64 or 128 bits. Otherwise the error is
  `sema_neon_vector_bad_size`, "Neon vector size must be 64 or 128 bits".
- The result is a `VectorKind::Neon` / `NeonPoly` vector (spec/types.md
  `Vector`).

## Mangling (`kiln_abi/src/mangle.rs`)

- On AArch64, a Neon vector mangles as its ACLE name `__<Elt>x<N>_t`,
  for example `10__Int8x16_t` or `14__Bfloat16x8_t` (clang
  `mangleAArch64NeonVectorType`).
- On other targets it mangles as `__simd64_<elt>` or `__simd128_<elt>`
  (clang `mangleNeonVectorType`).

## `target("...")` ([dcl.attr.grammar], clang `TargetAttr`)

- The attribute is parsed with an expression argument list
  (kiln_parse `takes_expr_args`).
- Sema accepts exactly one string literal. It stores the literal in the
  attribute (`AttrKind::TARGET`, `a` = the `StringLitId`), and the AST
  dump prints it as clang does.
- Feature names are not validated in sema; see the follow-ups.
