# WP-609 — Initializing a class from its own class never uses the source's conversion functions

[dcl.init.general]/16.6.2.1, [over.match.ctor]/1, [over.match.copy]/1,
[class.conv.fct]/1, [over.ics.user]/4, [temp.inst]/11. The rule is in
`spec/sema.md` §6 (class objects by constructor) and
`spec/sema-overload.md` §6.6.

- A conversion function (or a specialization of a conversion function
  template) converting an object of class `S` to a class `T` where `S` is
  `T` or derived from `T` is now a non-viable candidate
  (`CandidateFailure::TrivialConversion`, clang
  `ovl_fail_trivial_conversion`) in `add_conversion_candidate`
  (`crates/kiln_sema/src/overload/ics.rs`). Before, clang's CWG2327
  candidates (`add_elision_candidates`, `class/ctor_select.rs`) let such a
  function compete with the copy and move constructors, with four symptoms
  (all accepted by clang 19 and GCC):
  - a `D` member direct-list-initialized from a `D&&` chose
    `template <class T> explicit operator T()` with `T = D` (its implicit
    object parameter `D&` beat the copy constructor's `const D&`) and
    instantiated its `static_assert`ing body (a JSON library's result
    wrapper);
  - `It r = *this;` with `operator It<const T>()` being the class itself
    for `T = const int` was "ambiguous" (the copy-initialization set did
    not apply the constructor-over-conversion tie-break);
  - a prvalue passed by value chose a deleted `operator view() &&` naming
    the class itself: "call to deleted constructor";
  - `Less(c)` for `c` of a class derived from `Less` with an explicit
    `operator Less()` chose the conversion function (exact object match
    against the constructor's derived-to-base conversion), and the
    same/derived-class path of `construct.rs` (which, unlike
    `construct_class`, has no conversion-function branch) handed it to
    `use_ctor`, whose constructor access check on that member produced
    "calling a private constructor of class 'Less'". No constructor was
    private; the path is now unreachable for conversion functions.
- A copy-initialization from the same or a derived class no longer
  suppresses user-defined conversions on the constructor's parameter
  (`resolve_ctor_ex`, `class/ctor_select.rs`; [over.best.ics]/4 restricts
  only the copy-initialization of a class by user-defined conversion,
  [over.match.copy]): `A a = cb;` for a `const B cb` with `B : A`,
  `A(A&)` and `A(X)` selects `A(X)` through `B::operator X()` instead of
  "no matching constructor".
- -Wclass-conversion is no longer reported for a member of an
  instantiated class template (clang `ActOnConversionDeclarator`
  suppresses it for instantiations; `class/special/declare.rs`).
- A non-viable conversion function is noted after the constructors, as an
  arity mismatch (`overload/diag.rs`, clang `EffectiveFailureKind`).
- Audit of rule 2 (no definition instantiated to decide viability):
  candidate collection instantiates definitions only for a deduced return
  type (`deduced_return_mismatch`, `check_undeduced_use`), as clang does;
  constructor, conversion function and function templates losing to a
  non-template keep ill-formed bodies and noexcept-specifiers
  uninstantiated (`over.match.ctor/template-bodies-not-instantiated.cpp`).
  The conversion template body in the JSON-library shape was instantiated
  because the specialization was selected, not during viability.
