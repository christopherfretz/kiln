# Precompiled headers: current state (kiln 1.2.0, 2026-11-13)

A kiln PCH carries a snapshot of the whole front end at the end of its
header, and a consumer restores it; where it cannot, it processes the
header again (replay), which is always correct. That is the default
since WP-1404, and the only PCH path since WP-1397 retired kiln 1.1's
declaration image (`-fkiln-pch-image` is accepted and ignored with a
warning). The contract is spec/pch.md; the flags are spec/driver.md
"Precompiled headers"; the user's view is docs/USER_GUIDE.md
"Precompiled headers".

## Where it stands

- **Speed.** A `-fsyntax-only` consumer of `<bits/stdc++.h>` takes 0.57 s
  against 0.67 s for clang 19's PCH and 1.48 s for a replay; all 106
  libc++ 19 headers take 0.72 s against 0.52 s for clang (region `main`
  below; the PCH file's read dominates on a shared file system, next
  section). A producer takes one pass where it may (1409 of 1419 corpus
  producers, docs/status/pch-snapshot-gates.md "Default path"), else two
  (spec/pch.md "Producer").
- **Memory.** kiln's peak RSS is below clang's on every row, PCH or not.
- **Correctness.** docs/status/pch-snapshot-gates.md: the corpus with
  the synthetic prefix (5706 of 5707 consumers restored, the other the
  module unit, which always replays) and libc++ (3894 of 3894 restored)
  under `--pch-diff snapshot` match the plain build; the cases of
  `scripts/pch-snapshot-diff.sh` are the same in both producer shapes;
  the corruption fuzz never misreads a section
  (docs/status/pch-snapshot-hardening.md); `scripts/pch-release-gate.sh`
  runs these in the release gate.
- **Refusals.** A prefix whose state is not at rest at its end (a header
  ending in a global module fragment's `module;`, an open pragma
  attribute push, a module or carried-constant recording) gets a PCH
  without a snapshot and `-Wpch-snapshot-unused`; its consumers replay.
  A consumer whose configuration differs (spec/pch.md "Identity") warns
  and replays. Neither is an error unless `-Werror=pch-snapshot-unused`
  asks for it.
- **Versioning.** `crates/kiln_driver/pch-snapshot-format.txt` records
  each (format version, schema hash) pair; a PCH from another kiln build
  is replayed or rejected with a "rebuild" error, never misread
  (spec/pch.md "Format versioning").
- **Open.** The PCH file is read whole where clang maps it; the
  measurements of the next section show what that costs on a slow file
  system. docs/KNOWN_ISSUES.md lists the open PCH items.

The measurements of the retired image (regions `wp-1393-*` and
`wp-1401`, the carried-set census and the per-wave sections of WP-1293
to WP-1384) are in this file's history before WP-1397.

## WP-1404: the default path against wp-1401

Region `main` (default path, `f34affb18`) and the WP-1401 bench (the same
bench with `-fkiln-pch-snapshot=write`/`=load -O0`, `6e8989bba`), kiln
`-fsyntax-only` consumer, seconds:

- gnu: 0.57 (wp-1401 0.52), empty main 0.51 (0.39); replay 1.48 (1.42);
  clang 0.67 (0.65).
- lcx: 0.72 (0.37), empty main 0.62 (0.28); replay 1.47 (1.14); clang
  0.52 (0.42).
- mid: 0.27, empty main 0.22; meta: 0.29, empty main 0.20.

The consumer's own work did not get slower. The time went into reading
the PCH file. The same binary and the same PCH, read from the shared
file system the bench uses (`.build/`, virtiofs) and from the
container's local disk, interleaved, 7 runs each, empty main,
`-fsyntax-only` (load average 23):

| PCH on | gnu (35 MB) | lcx (40 MB) |
|---|---:|---:|
| shared file system | 0.47 s | 0.57 s |
| local disk | 0.32 s | 0.22 s |

`KILN_SNAP_TIMING=1` shows where: `pch record read` is 14 ms from the
local disk and 69-330 ms from the shared one, and so is the first read
of the section (`schema hash`, 14 ms against 57-195 ms); the restore and
the end of the unit are the same. The default producer writes the same
section as `=write -O0` (lcx: 41567217 bytes both ways, the same load
times). So the slowdown against wp-1401 is the host's file system at the
time of the run (wp-1401 ran at load 16-21, this one at 18-24 with
other builds on the same share), not the flip. A kiln PCH is read whole
(clang maps its file and reads what it needs), which is why its time
depends on the file system more than clang's does. To reproduce:

```sh
K=<release kiln++>
$K -std=c++26 -stdlib=libc++ -x c++-header bench/pch/lcx.h -o <dir>/lcx.pch
KILN_SNAP_TIMING=1 $K -std=c++26 -stdlib=libc++ -include-pch <dir>/lcx.pch \
  -fsyntax-only bench/pch/empty.cpp
```

with `<dir>` on each file system in turn.

## Setup

The numbers below are generated by `cargo xtask bench bench/pch --record`
(spec/bench.md "The pch group", WP-1294). Re-run that command after a PCH
change; `--record --label <name> --compiler <kiln++>` adds a region for
another build, such as a branch under review. Everything outside
the generated regions is hand-written and kept by the generator.

- kiln is the release build (`cargo build --release -p kiln_driver`),
  clang is clang 19 (Debian). Both run back to back on each row, on a
  shared aarch64 host whose load moves wall times about 1.4x, so the
  kiln-to-clang ratios are steadier than the absolute times. Peak RSS
  moves a few percent between identical runs (below); kiln's accounted
  memory does not.
- Each number is the median of 5 runs: wall time from the harness, peak
  RSS from `/usr/bin/time -f %M`.
- Header sets (`bench/pch/<case>.h`):
  - `gnu`: `#include <bits/stdc++.h>` (libstdc++ 14).
  - `lcx`: the 106 public libc++ 19 headers, one `#include` each, with
    `-stdlib=libc++`.
  - `mid`: `<algorithm>`, `<map>`, `<string>` and `<vector>`
    (libstdc++ 14).
  - `c`: `<stdio.h>`, `<stdlib.h>`, `<string.h>` and `<zlib.h>`, as C17
    (`-x c-header`, then `-x c` for the unit).
- The C++ translation unit (`bench/pch/<case>.cpp`) uses `std::vector`,
  `std::sort`, `std::map` and `std::string`, with no `#include`s of its
  own. The C one calls `strncpy`, `crc32`, `printf` and `atoi`.
- Rows (`-std=c++26`, or `-std=c17` for `c`). kiln's rows are the
  default path, the snapshot (since WP-1404, the region `main`):
  - "no PCH": `-include <case>.h`.
  - "PCH build": `-x c++-header <case>.h -o <case>.pch`, both compilers.
  - "PCH load": `-include-pch <case>.pch`, both compilers. The row names
    the path kiln took (`snapshot` when it restored).
  - "PCH replay": `-fno-kiln-pch-snapshot -include-pch <case>.pch`, kiln
    only: the 1.1 behaviour, from the same PCH.
  - `-O0 -c` rows write an object file; nothing is written to `/dev/null`.

## Reading the numbers

A kiln consumer that restores the snapshot is within about 1.3x of
clang's PCH consumer on the C++ header sets, and both are several times
faster than their own no-PCH builds (each case's "Wall time of PCH load
relative to no PCH" line). A replay costs the same as no PCH, within
noise: replay parses the header in full. The C set is too small for a
PCH to matter to either compiler.

### Memory noise and the accounted figure (WP-1303, 2026-11-11)

Five recordings of the `none` variants on one unchanged release
`kiln++` (load 10.6 to 17.2), 5 runs each:

- Peak RSS is not steady. The median moved by up to 6.4% between
  recordings (`c/none-syntax`, 13 MB), 3.5% (`gnu/none-obj`), and about
  2.2% (`gnu`, `lcx` and `mid` at `-fsyntax-only`). The minimum of the
  runs moved as much, and the high samples did not follow the load.
- kiln's accounted memory (`-fkiln-memory-report`, total reserved bytes)
  was byte-identical over 10 runs of every `none` variant and in two
  working directories, while the RSS of the same runs moved 4%. The
  noise is outside kiln's tables. Transparent huge pages (`always` on
  this host) are the suspect, unproven.
- At `-O0 -c` the RSS figure is the largest process, and for `mid` and
  `c` that is `llc`, not kiln (58 and 55 MB, against kiln's 56 and
  15 MB). Those rows measure LLVM.

So peak RSS is judged at 5% on every row, and the `none` rows are also
judged on the accounted figure at 2% (spec/bench.md "The pch group").

The re-record of 2026-11-11 (main `876dfe167`) reported six `-O0 -c`
rows of `mid` and `c` as about 10% smaller. Those rows are
llc-dominated, so this is not a kiln improvement.
